# Agent Harness (Local) — 2026-04-23

## Summary

The local agent stack has crossed a threshold this spring: llama.cpp
merged full MCP client support with an agentic tool-call loop in
March 2026, which means any GGUF model can now drive the same MCP
servers that Claude Code and Cursor use, without an external bridge.
On the harness side, **OpenCode** (Charm-maintained TUI), **Aider**,
**Plandex**, and the new **OpenHarness** (HKUDS, Apr 2026) are the
active projects for local-first workflows, while **Hermes Agent**
(Nous Research) ships with six runtime backends including Docker,
SSH, and serverless. On backends, **vLLM** dominates production-grade
tool-calling with measured ~3–4× lower TTFT and up to 16× throughput
vs. Ollama under load; **Ollama** wins on ergonomics; **LM Studio**
remains GUI-first but still lacks streaming and parallel tool-calls;
**SGLang** beats vLLM by ~29% on shared-prefix agent workloads.
For model+harness combos, the standout of the cycle is
**Qwen3-Coder-Next (80B MoE, 3B active)** — reported to execute
long-horizon tool-use chains on a single 64 GB Mac or RTX 5090, and
the default local pick for coding agents.

## Harnesses

### OpenCode (Charm)

- Source: <https://github.com/sst/opencode> (maintenance now under
  Charm); tutorials:
  <https://lushbinary.com/blog/opencode-ollama-local-ai-coding-privacy-guide/>,
  <https://aayushgarg.dev/posts/2026-03-29-local-llm-opencode/>,
  <https://medium.com/rigel-computer-com/opencode-llama-cpp-sovereign-local-and-what-nobody-tells-you-upfront-47471c060735>
- License: MIT (per upstream).

TUI-first coding harness that multiplexes across providers
(GPT-5, Claude 4.5 Sonnet, Qwen Coder, CodeLlama) and local models via
Ollama or llama.cpp. Strong story on "swap the model, keep the
agent". The Medium post above is worth reading for the gotchas —
context truncation defaults, tool-schema mismatches with smaller
local models, and the cost of not using a reranker in the built-in
RAG.

### Aider

- Source: <https://aider.chat/>
- License: Apache 2.0.

Still the reference point for terminal coding agents. Works with any
OpenAI-compatible endpoint (so Ollama, vLLM, LocalAI, llama.cpp
server). Lightweight harness — no long-running loop, mostly single
edits per turn — which is why it behaves well on smaller local
models that struggle to maintain coherent multi-step plans.

### Plandex

- Source: <https://plandex.ai/>
- License: MIT.

Terminal-based coding agent built around long horizons: claims a
~2M effective context with ~20M tokens indexed via Tree-sitter.
Plans are an explicit data structure, which gives you checkpointing
and recovery that most harnesses don't have. Worth pairing with a
model that is strong at structured output (Qwen3-Coder-Next).

### OpenHarness (HKUDS, April 2026)

- Source: <https://github.com/HKUDS/OpenHarness>
- License: see repo (open source).

Research-focused reference implementation of a production-grade
agent harness, released in April 2026 with a built-in "Ohmo"
personal agent. Useful as a teaching artifact and as a base for
papers, not yet a daily driver.

### Hermes Agent (Nous Research)

- Source: <https://github.com/nousresearch/hermes-agent>

Interesting because it ships six *terminal backends*: local,
Docker, SSH, plus serverless runners (Daytona, Modal). If you want
the agent to do destructive things, the Docker/SSH sandboxes are a
practical containment story.

### llama-agent

- Source: <https://github.com/gary149/llama-agent> (fork:
  <https://github.com/TuringWorks/llama-agent>)

A deliberately minimal agent loop for small local models: one loop,
a few built-in tools, MCP support. Good baseline when evaluating
whether you actually need a heavier harness.

## Backends

### llama.cpp

- Source: <https://github.com/ggml-org/llama.cpp>
- MCP merge announcement:
  <https://aiproductivity.ai/news/llamacpp-merges-mcp-support-agentic-loop/>
- Function-calling docs:
  <https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md>

In March 2026 PR #18655 merged full MCP client support into
llama-server's web UI: MCP server management, tool calls, an
agentic loop, MCP Prompts and Resources. For local users this is
the biggest change of the year — any GGUF model is now one config
away from the same MCP ecosystem Claude Code uses.

### vLLM

- Benchmarks:
  <https://developers.redhat.com/articles/2025/08/08/ollama-vs-vllm-deep-dive-performance-benchmarking>,
  <https://www.sitepoint.com/ollama-vs-vllm-performance-benchmark-2026/>,
  <https://allenkuo.medium.com/vllm-or-ollama-on-blackwell-benchmarks-landmines-and-what-agents-actually-need-5dc539bb28ef>

Production-grade serving: continuous batching, PagedAttention,
prefix caching. Published measurements in 2026 show ~3.9× lower
TTFT, ~3.4× faster prefill, ~2.8× higher concurrent throughput vs.
Ollama, and up to ~16× throughput under concurrent load. Good
tool-calling and parallel function-call support. The cost is
configuration complexity.

### SGLang

- See: <https://theaiengineer.substack.com/p/vllm-vs-ollama-vs-sglang-vs-tensorrt>

For workloads where agents share large amounts of prompt prefix
(chatbots, RAG, multi-turn coding), SGLang reportedly beats vLLM by
~29% on throughput thanks to RadixAttention-style prefix sharing.
The sweet spot is multi-tenant agent serving.

### Ollama

- See Red Hat / SitePoint benchmarks above.

Default for local dev. Single command to pull + run. Good tool-call
support for the supported model families, but falls far behind vLLM
under concurrency. Use for prototyping and for single-user desktop
agents.

### LM Studio

- See: <https://www.aimadetools.com/blog/ollama-vs-lm-studio-vs-vllm/>,
  <https://medium.com/@dtiberiusg/ollama-vs-vllm-vs-lm-studio-privacy-first-ai-runtime-comparison-2026-116f442f888a>

Best GUI for experimentation. 2026 reporting still flags two
limitations: **no streaming tool calls** and **no parallel function
invocation**. Fine for interactive use; not ideal as an agent
backend in production.

### LocalAI

- Source: <https://localai.io/>

Bundles several backends behind an OpenAI-compatible API. Often the
lowest-friction way to port an existing OpenAI agent to local
models: typically a single base-URL change.

### TensorRT-LLM

For NVIDIA data-center hardware. Best raw throughput on supported
architectures, but operationally heavier than vLLM/SGLang and less
relevant to single-workstation local setups.

## Model + Harness Combinations That Work Well

### Tiny (≤4B)

- **Llama-3.2-3B / Qwen2.5-3B + llama-agent** on llama.cpp.
  Works for simple tool-use and single-file edits; plan-heavy tasks
  fail. Source:
  <https://github.com/gary149/llama-agent>,
  <https://unsloth.ai/docs/basics/tool-calling-guide-for-local-llms>.
- **Phi-4-mini + Aider** on Ollama. Fine for small-diff coding,
  brittle on multi-file reasoning.

### Small (4B–14B)

- **Qwen2.5-Coder-7B/14B + Aider** on Ollama or vLLM. Solid default
  for "laptop coding assistant" scenarios; handles Aider's
  single-turn edit workflow reliably.
- **Llama-3.1-8B-Instruct + OpenCode** on llama.cpp. Adequate for
  light agentic loops once you enforce a strict tool-call schema.

### Medium (14B–32B)

- **Qwen3-32B + OpenCode + vLLM**. Reported as the practical
  sweet-spot for a 24–48 GB single-GPU workstation running a proper
  agent loop. Source:
  <https://dev.to/sienna/qwen3-coder-next-the-complete-2026-guide-to-running-powerful-ai-coding-agents-locally-1k95>.
- **DeepSeek-Coder-V2-Lite (16B MoE) + Plandex** on vLLM. Benefits
  from Plandex's explicit plans on longer tasks.

### Large (32B–70B)

- **Llama-4 Scout / Maverick class + OpenCode + vLLM**. Good general
  agent. Source:
  <https://www.spheron.network/blog/deepseek-vs-llama-4-vs-qwen3/>.
- **DeepSeek-V3.2 dense variants + Aider** when available.

### XL / MoE (>70B total, incl. 100B+ MoE)

- **Qwen3-Coder-Next (80B total, 3B active) + OpenCode or Plandex**
  on llama.cpp or vLLM. The standout pick this cycle: runs on a
  64 GB Mac, RTX 5090, or AMD 7900 XTX with 256K context, handles
  long-horizon tool-use and error recovery in the coding domain,
  Apache-2.0. Sources:
  <https://huggingface.co/Qwen/Qwen3-Coder-Next>,
  <https://unsloth.ai/docs/models/qwen3-coder-next>.
- **Kimi K2 Thinking + OpenHarness / OpenCode**. Noted in 2026
  comparisons for handling 200–300 sequential tool calls without
  derailing — the top open model on long-horizon agentic tasks.
  Source:
  <https://www.spheron.network/blog/deepseek-vs-llama-4-vs-qwen3/>.
- **DeepSeek-V3.2 full + vLLM + Plandex / OpenCode**. High-quality
  but heavy; best on multi-GPU servers, not workstations.
