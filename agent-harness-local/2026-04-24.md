# Agent Harness (Local) — 2026-04-24

## Run metadata

- **Date:** 2026-04-24
- **Window covered:** ~Nov 2025 – Apr 2026
- **Scope:** Agent harnesses, serving backends, and model combos for **local / self-hosted open-weights LLMs**.

## TL;DR

The "local coding agent" story has stabilized around a small set of clear winners. For harnesses, **OpenHands** explicitly recommends **Qwen3-Coder-30B-A3B-Instruct** and **Devstral Small 2 (24B)** for local use and supports Ollama / SGLang / vLLM out of the box; **Aider**, **Cline**, **Roo Code**, and the **Codex CLI** (`--oss` flag) are the other mature paths. On the backend side, **vLLM** is the most complete for production tool-calling, **llama.cpp** `llama-server` has closed the biggest feature gap by adding a built-in **MCP client**, **Ollama** adopted **MLX** kernels on Apple Silicon, and **TGI** is now officially in maintenance mode with HF redirecting users to vLLM / SGLang. The single most common failure mode is a **chat-template / tool-call-parser mismatch** — Qwen themselves recommend *not* using vLLM's Hermes auto-parser for Qwen3, and Qwen2.5-Coder needs a dedicated parser fork because its `<tools>` tag format is not Hermes-compatible.

## Harnesses / frameworks

### Coding-agent CLIs / IDE harnesses

- **OpenHands** (formerly OpenDevin) — [docs](https://docs.openhands.dev/openhands/usage/llms/local-llms). Actively maintained. Official local picks: **Qwen3-Coder-30B-A3B-Instruct** and **Devstral Small 2 (24B)**. Backend support: Ollama, SGLang, vLLM. Known issue: Qwen3 can emit correct thinking but skip tool calls when the parser is misconfigured ([#8140](https://github.com/OpenHands/OpenHands/issues/8140)).
- **Aider** — [docs](https://aider.chat/docs/llms.html). Still the reference for git-native pair programming. Works with any OpenAI-compatible local endpoint (Ollama, llama.cpp, vLLM). Aider's own leaderboard remains the canonical benchmark cited for local coding models.
- **Cline & Roo Code** (VS Code). Both BYO-key; Roo Code is reported more optimized for fully-local setups ([Roo Code local-models docs](https://docs.roocode.com/advanced-usage/local-models), [LM Studio provider](https://docs.roocode.com/providers/lmstudio)), with per-mode model routing.
- **Continue**. Active; IDE assistant supporting local models via Ollama / OpenAI-compatible APIs.
- **Codex CLI (OpenAI)** — `--oss` flag against Ollama / LM Studio / MLX / llama.cpp / vLLM ([Ollama integration](https://docs.ollama.com/integrations/codex)). Requires ≥64k context. Advertised local targets: `gpt-oss:20b` and `gpt-oss:120b`.
- **Goose (Block)** — [GitHub](https://github.com/block/goose). Apache-2.0, ~29k stars, first-class Ollama / Docker Model Runner / Ramalama support. Independent testing ([Techbuddies Jan 2026, medium confidence](https://www.techbuddies.io/2026/01/22/goose-vs-claude-code-how-a-free-local-ai-agent-challenges-200-a-month-coding-tools/)) reports ~20% higher error rate vs. Claude Opus on complex multi-step tool chains with Llama 4 via Ollama — but zero cost and fully private.
- **Qwen-Agent** — [GitHub](https://github.com/QwenLM/Qwen-Agent). Maintained by the Qwen team. Recommended over external parsers for Qwen3-family tool calling; ships its own parser, MCP support, code interpreter.
- **Plandex** — [GitHub](https://github.com/plandex-ai/plandex). Terminal-based, multi-step, designed for large codebases; Dockerable, BYO-key or OpenRouter. Still active.
- **SWE-agent**. Academic research harness, defines the Agent-Computer Interface pattern. More a benchmark baseline than a daily driver.
- **Letta Code** — [blog](https://www.letta.com/blog/letta-code), [GitHub](https://github.com/letta-ai/letta). Memory-first coding agent; model-agnostic; local-LLM usable but not the primary target.
- **Devika**. Appears less active in 2026 than 2024–25 by search visibility; treat as legacy.

### Orchestration frameworks (library-level)

- **LangGraph** — reportedly passed CrewAI in GitHub stars in early 2026 ([Medium, Mar 2026, medium confidence](https://medium.com/data-science-collective/langgraph-vs-crewai-vs-autogen-which-agent-framework-should-you-actually-use-in-2026-b8b2c84f1229)). Production choice (checkpointing, replay, audit trails). Works with any local OpenAI-compatible endpoint.
- **Smolagents (HuggingFace)** — [GitHub](https://github.com/huggingface/smolagents). Lightest-weight, **code-as-tool-calls** (agent writes Python instead of JSON). Reported best-in-class for local LLMs because it bypasses fragile JSON tool-call parsing ([DEV.to, 2026, medium confidence](https://dev.to/pooyagolchian/ai-agents-in-2026-langgraph-vs-crewai-vs-smolagents-with-real-benchmarks-on-local-llms-4ma1)).
- **CrewAI**. Fastest prototyping (role DSL). Local-capable but adds latency.
- **AutoGen (Microsoft)**. Still active, conversational multi-agent focus.
- **Agno** (formerly Phidata). Multi-modal, multi-agent; local-model friendly.
- **Dify** — [dify.ai](https://dify.ai/). Drag-and-drop flow builder; Ollama + OpenAI-compatible support.

## Serving backends

| Backend | 2026 tool-calling state |
|---|---|
| **vLLM** ([tool-calling docs](https://docs.vllm.ai/en/latest/features/tool_calling/)) | Most complete. `--enable-auto-tool-choice` + `--tool-call-parser {hermes,llama3_json,mistral,...}`. Supports `tool_choice=auto/required/none/named`. Parallel calls OK. `strict` accepted but no-op. Open streaming-parser bugs ([#31871](https://github.com/vllm-project/vllm/issues/31871), [#19056](https://github.com/vllm-project/vllm/issues/19056)). |
| **SGLang** | Close second; strong on agentic / tool-use / multimodal. Documented support for GLM-4.5 / 4.6 tool parsers and Qwen3. |
| **llama.cpp** (`llama-server`) | Late-2025/2026 added **built-in MCP client** (`--webui-mcp-proxy`); biggest feature gap-closer vs. Ollama. Hermes / llama3 tool parsers. |
| **Ollama** | Tool calling works for Llama 3.1/3.2, Qwen2.5/3, Mistral. Still no `tool_choice` forcing and no streaming tool-calls. Unsloth landed Qwen3-Coder tool-call fixes usable across Ollama / llama.cpp / LM Studio / Open WebUI ([Unsloth guide](https://unsloth.ai/docs/models/tutorials/qwen3-coder-how-to-run-locally)). **Adopted MLX on Apple Silicon** in Mar 2026 ([9to5Mac](https://9to5mac.com/2026/03/31/ollama-adopts-mlx-for-faster-ai-performance-on-apple-silicon-macs/)). |
| **LM Studio** | GUI + OpenAI-compatible server; de-facto easy path for desktop users. Works with Roo Code / Cline / Codex CLI. |
| **MLX / mlx-lm** | The Apple Silicon answer. M4 Max 128GB reports ~31–44 tok/s on well-fitted models; Ollama now delegates to MLX on Macs. |
| **TGI (HuggingFace)** | **Maintenance mode** as of 2026 — HF directs users to vLLM or SGLang. Multi-backend wrapper for TRT-LLM / vLLM exists. |
| **TensorRT-LLM** | Raw-speed leader on NVIDIA (2–5× claims), but niche; complex build path. |
| **ExLlamaV2** | Still the go-to for tight-VRAM GPTQ/AWQ/EXL2 quants; less prominent for tool-calling agents. |
| **KoboldCpp** | GGUF-based, chat/roleplay focused; not a primary agent backend. |
| **Aphrodite** | Listed alongside vLLM / TGI as optimization option; smaller 2026 footprint. |

**Key gotcha:** For Qwen3 with vLLM, Qwen themselves recommend *not* using `--enable-auto-tool-choice --tool-call-parser hermes` and instead using **Qwen-Agent's built-in parser** ([Qwen function-calling docs](https://qwen.readthedocs.io/en/latest/framework/function_call.html)). Qwen2.5-Coder uses a different `<tools>` tag format and silently fails against the Hermes parser — there's a community fork [`vllm-qwen2.5-coder-tool-parser`](https://github.com/hanXen/vllm-qwen2.5-coder-tool-parser).

## Model × backend × harness combos

### Small (≤ 8B)

1. **Llama 3.1 8B Instruct + Ollama + Aider / Smolagents** — function-calling officially supported; easiest path. *Gotcha:* 8B is marginal for multi-step tool chains; expect retries.
2. **Qwen3 8B + vLLM (Qwen-Agent parser) + OpenHands** — Hermes-style tool format works once parser is correct. *Gotcha:* use Qwen-Agent's parser, not vLLM's auto parser.
3. **Phi-4-mini (instruct) + llama.cpp + Continue / Smolagents** — strong reasoning per-param; use Phi's own recommended chat and function-calling formats. *Gotcha:* Phi tool-call format is **not drop-in** compatible with the Llama3 JSON parser.
4. **Gemma 3 4B + Ollama + Dify / Smolagents** — native JSON function calling. *Gotcha:* small context vs. agent tasks.

### Medium (8–32B)

1. **Qwen3-Coder-30B-A3B-Instruct (MoE, 3B active) + Ollama or vLLM + OpenHands / Cline / Qwen Code** — OpenHands' own #1 local pick ([model card](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct)); 256K native context (1M via YaRN); tool-call format purpose-built for agents. *Gotchas:* use Unsloth-patched GGUF for correct tool-call tokens; on vLLM, use Qwen-Agent parser; Q4_K_M (~17 GB) fits a 24 GB card with headroom.
2. **Devstral Small 2 (24B) + vLLM + OpenHands** — co-designed by Mistral × All Hands specifically for SWE agents. *Gotcha:* Mistral tool-call format — use `--tool-call-parser mistral`.
3. **Mistral-Small 3 / 3.1 + vLLM + LangGraph / CrewAI** — trained for rapid function execution and JSON-structured output in agentic workflows ([Mistral function-calling docs](https://docs.mistral.ai/capabilities/function_calling)).
4. **Qwen2.5-Coder 32B + llama.cpp + Aider** — historically competitive with GPT-4o on Aider's own benchmark. *Gotcha:* not Hermes tool format — needs the dedicated Qwen2.5-Coder tool parser if you want vLLM tool use.

### Large (32–100B)

1. **Llama 3.3 70B Instruct + vLLM (TP=2 on dual 24 GB) + LangGraph / Aider** — Llama 3.x still leads BFCL tool-use benchmarks. *Gotcha:* needs ~40 GB at 4-bit AWQ + KV; dual-GPU or 48 GB-class card.
2. **GLM-4.5-Air (106B total, 12B active MoE) + SGLang + Cline / Roo Code** — hybrid thinking / non-thinking, strong agent/tool use. *Gotcha:* use z.ai-supplied chat template; tool parser in vLLM / SGLang is GLM-specific.
3. **Qwen3-72B-class dense + vLLM TP=2/4 + OpenHands** — if you need dense rather than MoE. *Gotcha:* VRAM-hungry; MoE variants usually a better deal.
4. **Qwen3-Coder-Next (80B total / 3B active, per HF) + vLLM + OpenHands** — built for coding agents, cheap activation cost. *Gotcha:* newer, less community-tested; treat "works flawlessly" claims cautiously.

### XL (100B+, MoE)

1. **DeepSeek V3 (671B / ~37B active) + vLLM + Docker + LangGraph / Aider** — workstation deployment viable (32 GB RAM + 12 GB+ VRAM with offload) but real production wants multi-GPU. *Gotcha:* chat template for tool calling was revised — use current template; thinking-with-tools mode is non-trivial.
2. **DeepSeek R1 / R1-Distill + vLLM or Ollama + Aider / Smolagents** — reasoning-first; distills are the realistic local option on a 4090.
3. **GLM-4.6 (355B total / 32B active) + SGLang + Claude Code / Cline / Roo Code / Kilo Code** ([model page](https://huggingface.co/zai-org/GLM-4.6), [Unsloth run-local guide](https://docs.unsloth.ai/models/glm-4.6-how-to-run-locally)). 200K context, explicit tool-use training. *Gotcha:* needs multi-GPU or heavy quantization; z.ai's chat template required.
4. **Kimi K2 + vLLM (multi-node) + LangGraph** — #1 on Tau2-Bench Telecom (agentic customer support) at release. *Gotcha:* real multi-GPU territory.
5. **Llama 4 Scout / Maverick** — Scout (10M context) is the "fits on smaller rigs" option; Maverick needs serious hardware (400B total / 17B active). *Gotcha:* mixed reports on tool-call reliability; Gemma / Qwen / GLM currently have better-tested tool-use paths in the community.

## Recommendations

- **Single RTX 4090 (24 GB):** Run **Qwen3-Coder-30B-A3B-Instruct** at Q4_K_M (~17 GB) on **llama.cpp** (or Ollama for one-command simplicity), wired to **OpenHands** or **Cline / Roo Code** for interactive coding and **Aider** for git-first edits. Best-tested stack today: OpenHands officially recommends it, tool-call parsers work post-Unsloth fixes, and there is headroom for agent context. Alternate dense pick: Qwen2.5-Coder 32B at Q4 with Aider.
- **Mac M4 Max (64–128 GB):** Use **MLX / mlx-lm** (or the MLX-backed Ollama build) serving **Qwen3-Coder-30B-A3B** at 4-bit; drive it with **Codex CLI** (`--oss`), **Goose**, or **Cline**. Unified memory allows a 64B-class MoE at 4-bit on 128 GB, but tool-call maturity is better on Qwen3-Coder than on most alternatives at that size.
- **Multi-GPU rig (2–8× 24–80 GB):** **vLLM** with tensor parallelism (TP=2/4) serving **GLM-4.6**, **Llama 3.3 70B**, **Devstral Small 2**, or **DeepSeek V3** depending on VRAM; point **LangGraph** (production) or **OpenHands** (interactive) at the OpenAI-compatible endpoint. If you need best-possible agent benchmarks locally and have the hardware, **Kimi K2** via vLLM is the aggressive pick but expect tuning work. Across all rigs, prefer **Smolagents** if JSON tool-call parsing keeps breaking — having the model emit Python sidesteps most parser mismatches.

## Caveats

- A number of search hits referenced model names this run could **not independently verify** against primary sources: GLM-5 / GLM-5.1 / GLM-4.7, Qwen3.5 / 3.6, DeepSeek V3.2 (as opposed to V3.2-Exp which exists), Gemma 4, and NVIDIA "NemoClaw". Where this file mentions such names it is because they appear in citable upstream material (e.g. Unsloth run-local guides, vendor HF pages); otherwise they are intentionally omitted. Treat these references as approximate pending direct vendor confirmation.
- Several of the "works well" claims (Smolagents > JSON-tool harnesses for local LLMs; LangGraph overtaking CrewAI in stars; Goose 20% error gap vs. Claude) come from **blog / aggregator posts**, marked inline as medium confidence.
- Kimi K2 sub-version names (K2.5 / K2.6) seen in some search results were not independently verified and have been collapsed to "Kimi K2" here.
