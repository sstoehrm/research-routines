# LLM Memory — 2026-09-12

## Summary

The Aug–Sep 2026 cycle continued last cycle's shift from *frameworks* to
*decomposition papers*, but with a new emphasis on the **test-time
training** family (which was under attack in July's "Beyond Perplexity")
and on **stage-wise diagnostics** for existing memory stacks. Three TTT
papers landed in the window — TTCD, E2-TTT (with code), and Modular
TTT (with code) — which effectively answer "Beyond Perplexity" by
publishing behavioural results and public design spaces rather than
perplexity-only claims. On the evaluation side, MemGauge, Harness the
Memory, and Measure Before You Manage each pick a different axis
(utility-vs-risk, substrate choice, working-memory-object type) that
prior aggregate benchmarks collapsed away. Two decision-quality memory
papers stand out for local users: **MemArbiter** posts +20.9 pp on
ALFWorld under a 500-token budget with an open-weight backbone, and
**PMCoder** posts +5 pp on SWE-bench Verified by coupling episodic
memory with a phase planner. The security thread from July resolved
into a first defence paper — **Proof-of-Execution Memory** — which
notes that SENTINEL (the July FARMA defence) collapses to 0% under a
one-shot LM rewording attack. Framework side: MemOS shipped v2.0.30 →
v2.0.33 plus five weekly local-plugin drops; mem0 quietly *removed*
its "Dream" consolidation from four plugins; supermemory rolled a
critical vector-recovery patch (0.0.8); Cognee jumped v1.5.0 → v1.5.4
with security hardening and Linear/GitHub App integrations; Graphiti
finally shipped a Neo4j custom-database fix that had been silently
routing to `neo4j` for months. Model baseline: **Qwen3.8-Max** open
weights (2.4T MoE, 1M context) landed 12 Aug under a custom license —
the second 1M-context Max-class open release after DeepSeek V4-Pro
GA'd on 13 Aug. **OKF v0.2** added optional provenance/trust fields on
25 Jul.

## MemArbiter — Decision-Time Memory Arbitration for Long-Horizon Agents

- Source: <https://arxiv.org/abs/2608.02113>
- Date: 2026-08-03

### Why it matters for local models

Introduces the **Memory-Action Gap**: even when the right memory is
accessible, it can fail to shape the current action because it is
poorly formed, prioritised, or presented. MemArbiter is a
function-aware arbitration layer that operates at *decision time*
rather than at storage/retrieval, and — crucially — the reported
numbers are with an **open-weight** action-generation model, so this
is directly reproducible on a local stack.

### In-depth insights

- Decomposes interaction history into atomic items across **five
  functional Memory Banks**, combining bank-level demand, item-level
  relevance, focal-ambient representations, and a temporal presentation
  gate.
- ALFWorld: **82.8% success @ 500-token budget** and **92.5% @ 750-token
  budget** — **+20.9 pp** and **+25.4 pp** over the strongest baseline
  respectively.
- Also improves post-failure recovery and reduces failed-action
  repetition. Code/license not confirmed from the abstract page.

## TTCD — Learning What to Remember via Test-Time Context Distillation

- Source: <https://arxiv.org/abs/2608.01672>
- Date: 2026-08-03 (Princeton / UCB / UCSC / CMU — Wang, Dang, Zhu,
  Wen, Fu, Chai, Lee)

### Why it matters for local models

Self-supervised TTT objective: a **long-window teacher** supervises
the **fast weights of a short-window student**, using hidden-state
discrepancy as the dense signal — no labelled memory data required.
That means a local operator can bolt this onto their own long-context
runs without needing a labelled long-memory corpus. First serious
answer to July's "Beyond Perplexity" critique of TTT: behavioural
results on long-context language modelling rather than perplexity
alone.

### In-depth insights

- IP-TTCD (the interpolated-past variant) **consistently outperforms
  DeltaNet, Gated DeltaNet, sliding-window attention, and prior TTT**
  when pre-trained from scratch on long-context language modelling.
- No public code URL surfaced in the search results (unlike E2-TTT
  and Modular TTT); watch the arXiv page for a companion repo.

## E2-TTT — Expressive and Efficient Test-Time Training

- Source: <https://arxiv.org/abs/2608.21308>
- Code: <https://github.com/zeyun-zhong/E2-TTT>
- Date: 2026-08-21 (revised 2026-08-26)

### Why it matters for local models

Closes the perceived expressivity-vs-hardware gap that had discouraged
open-source TTT deployment. Hybrid design: **sliding-window attention
for local interactions + TTT state for cross-chunk history**, with a
closed-form state transition under the standard chunk-start gradient
approximation that exactly reproduces the per-token recurrence's
chunk-end fast-weight and momentum. That is, chunk-level training is
fully parallelisable **without** discarding the temporal structure
that prior chunk-wise methods threw away.

### In-depth insights

- Validated by training models up to **1.3B parameters from scratch**;
  performance is **on par** with previous TTT and hybrid-attention
  baselines on language modelling and **outperforms** them on
  in-context retrieval.
- Public GitHub with an official implementation — the first TTT paper
  in the window with a reproducible codebase for a workstation.

## Modular TTT — Composable Modules for TTT Design

- Source: <https://arxiv.org/abs/2608.07110>
- Code: <https://github.com/ByteDance-Seed/Modular-TTT>
- Date: 2026-08-07 (Tang, Qin, Pan, Li, Liu, Zhang — ByteDance-Seed
  et al.)

### Why it matters for local models

Framework paper, not an architecture. Represents the inner learner as
a **directed acyclic graph** and exposes fast-weight network, loss,
learning rate, weight decay, and normalisation as first-class design
dimensions. Auto-composes primitive-level train-view forward /
backward / causal query-view rules into the full graph-level TTT
computation. If TTT becomes a serious substrate for long-term memory,
this is the "hook system" you build against on a local box rather than
rewriting each variant.

### In-depth insights

- Companion repository from ByteDance-Seed on GitHub; the paper
  positions Modular TTT as the missing infrastructure that made the
  parallel proliferation of Titans / MIRAS / TTT-Done-Right / Gated
  DeltaNet / DeltaNet variants hard to compare.
- Ablations focus on isolating the role of each design dimension, not
  on beating a leaderboard.

## LongCat Sparse Attention — Hardware-Aligned Long-Context Substrate

- Source: <https://arxiv.org/abs/2608.01662>
- Date: 2026-08-03 (revised 2026-08-04; Meituan LongCat team)

### Why it matters for local models

DeepSeek Sparse Attention (DSA) is the current reference for
long-context serving in the open-weight world, but its Lightning
Indexer is **O(L²) and hardware-inefficient**. LSA is a co-designed
successor — the sort of change that shows up as latency-per-token on a
single-GPU serving stack running Qwen3.8 / DeepSeek V4 / Nemotron 3.

### In-depth insights

Three complementary strategies:

1. **Streaming-Aware Indexing** — turns scattered KV entries into
   hardware-aligned contiguous layouts so HBM reads coalesce.
2. **Cross-Layer Indexing** — amortises indexing overhead by reusing
   indexer outputs across consecutive layers via cross-layer
   distillation.
3. **Hierarchical Indexing** — coarse-to-fine scoring that
   progressively narrows the candidate set per query.

No code URL surfaced in the search results; the paper positions LSA
as the follow-up to DSA rather than as a from-scratch new attention.

## Learning How to Forget — Fine-tuning for Long-Context Sparse Attention

- Source: <https://arxiv.org/abs/2608.19920>
- Date: 2026-08-20 (Seeger, Zhang, Patil, Benidis, Schelter)

### Why it matters for local models

The one number every local operator will notice: the method **fits on
a single A100 40 GB**. It fine-tunes a model to co-adapt with **any KV
cache policy**, so it composes with LSA / DSA / PyramidKV / whatever
your local serving stack already uses. Trained models **often
outperform models trained with exact attention** on the same tasks —
i.e. the sparse regime is not merely a compression tax.

### In-depth insights

- KV cache selection and compression via sparse attention for
  long-context inference on moderate hardware.
- Policy-agnostic: fine-tuning doesn't bake in a specific eviction
  rule, so the same checkpoint can serve different budgets at
  inference.

## KVShareArena — KV-Cache Reuse Across Contexts and Model Checkpoints

- Source: <https://arxiv.org/abs/2609.10266>
- Date: 2026-09-09 (Xi Shi, Qian Lou — UCF)

### Why it matters for local models

The successor benchmark to the C²KV thread from the last cycle.
Existing serving systems only reuse KV when the reused text sits at
the **very start** of the prompt; the two workloads that dominate
local agentic stacks — **RAG** (chunks assembled per query) and
**multi-agent coordination** (reports written by other agents) — break
this. KVShareArena is the reference test that says "your KV-as-memory
scheme actually works" or does not.

### In-depth insights

- Scores every method by the **fraction of the gap** it recovers
  between "no cache" and "full recomputation," and *charges* compute,
  memory, and per-request latency, reporting cache-build cost
  separately.
- Correcting positions (no recompute) is enough for single-source
  questions; **multi-source questions require re-encoding part of the
  cache or retraining**, and only those methods recover half to
  two-thirds of the gap. **Unrepaired caches can be *worse* than no
  cache** — the paper's headline warning for anyone naively enabling
  cross-context KV reuse.

## PMCoder — Coupling Planning with Episodic Memory for Code Agents

- Source: <https://arxiv.org/abs/2608.06811>
- Date: 2026-08-07 (Zhang, Zhang, Huang)

### Why it matters for local models

Long trajectories in issue-resolution agents (tens to hundreds of
steps) are exactly where local open-weight agents lose to closed
frontier models. PMCoder makes the **planner and memory bidirectional**
(plan phase conditions memory retrieval; memory-derived trajectory
stats inform stuck-detection and replanning) rather than treating
them as independent modules. This is the pattern most likely to
transfer into Letta / mem0 / MemOS as an integration example.

### In-depth insights

- **SWE-bench Verified: +25 more resolved cases (+5.0 pp)** over a
  harness-matched baseline.
- Gains **persist even where the reproduction gate never fires** — so
  the win is not just "we noticed the tests early."
- Positions episodic memory as a state-tracking substrate for the
  planner, not just a retrieval index.

## GraphMemix — Query-Aware Evidence Forests for Multimodal Memory

- Source: <https://arxiv.org/abs/2608.26983>
- Date: 2026-08-27 (Li, Wang, Li, Hao, Peng — Peking University +
  MemoraX AI)

### Why it matters for local models

Naive embedding similarity retrieves incomplete, redundant, or
conflicting context; expensive question-agnostic offline summaries
solve that but cost tokens. GraphMemix formalises the problem as
**query-aware evidence-forest construction under a maximum evidence
budget** — a combinatorial-optimisation view of graph memory that
lands closer to how a local operator actually budgets context.

### In-depth insights

Three components:

1. **Candidate graph construction** — expands multi-view seed
   memories through schema and semantic relations.
2. **Evidence utility + activation costs** — decouples direct memory
   support from anchor-conditioned relation verification to suppress
   redundant/conflicting information.
3. **Forest optimisation** — jointly selects a forest-format memory
   context under a maximum evidence budget along with its reliable
   relational structure.

No open-weights or code URL surfaced in the abstract discovery; treat
as a design pattern rather than a drop-in library for now.

## MemGauge — Stage-Wise Utility-Risk Trade-offs

- Source: <https://arxiv.org/abs/2608.30177>
- Date: 2026-08-31

### Why it matters for local models

MemFail (last cycle) attributed failures to memory stages. MemGauge
does the parallel job for **security**: it separately varies
**writing admission**, **management policy**, and **retrieval
exposure** under matched clean / poisoned conditions, so you can tell
which stage of *your* local memory stack is where the risk actually
lives. Complements the FARMA / Proof-of-Execution Memory thread.

### In-depth insights

- Evaluated across **11 LLMs and two long-term memory benchmarks**.
- Three distinct stage profiles observed:
  - **Writing:** threshold-like — risk near zero until enough content
    is stored, then jumps sharply.
  - **Management:** policy can shift risk dramatically while barely
    changing utility (i.e. utility and risk are *decouplable* here).
  - **Retrieval:** utility gains and risk grow together — retrieval
    exposure is the axis you can't cheat.

## The Sleeping Agent — What Gist Compression Actually Loses

- Source: <https://arxiv.org/abs/2608.11775>
- Date: 2026-08-12 (Kyrkewood)

### Why it matters for local models

Direct empirical answer to a decision every local memory stack has to
make: do you gist-compress old context, or do you keep raw episodes
(MemMachine-style)? The paper uses **Salience-Weighted Consolidation
(SWC)** — a biologically-inspired frame explicitly modelled on
sleep-based consolidation — as a *diagnostic probe*, not as a
proposed system, so the finding is not tied to a particular framework.

### In-depth insights

- Gist compression **substantially outperforms truncation on
  multi-hop reasoning and single-hop factual QA**.
- Gist compression **substantially hurts temporal questions** — so
  any "when did this happen" workload needs a non-gist channel.
- 7 pages, 5 tables + appendices; code and results claimed available
  from the paper page.

## Harness the Memory — Holistic Substrate Evaluation

- Source: <https://arxiv.org/abs/2608.15008>
- Date: 2026-08-15 (Huang, Zhang, Wu, Chen, Jiang, Yang, Yang, Zou,
  Zhang, Wu, Wu, Chang, Yu, Liu, Caliskan)

### Why it matters for local models

The most complete "which substrate should I use?" study to date.
Covers **dense and sparse indices, text records, structural stores,
hierarchical stores, refinement-based memories, parametric updates,
and activation-compatible context mechanisms** — i.e. every category a
local operator would consider. Uses **26 performance and efficiency
metrics** across three backbone models and four benchmark suites.

### In-depth insights

- Headline finding: **no single substrate dominates**. Broad retrieval
  helps long-context factual QA; excessive retrieval **hurts sequential
  decision-making** by shifting attention away from action-critical
  context. This is a strong caution against defaulting to "just index
  more."

## Measure Before You Manage — Working Memory in Coding Agents

- Source: <https://arxiv.org/abs/2608.31057>
- Date: 2026-08-31 (Chen, Wan, Sun, Ma, Yang, Yan, Di, Cappello,
  Thakur)

### Why it matters for local models

Working memory in a coding agent is **heterogeneous**: instructions,
artifacts, tool outputs, and agent-generated state have different
sizes, retention curves, and representation profiles. Prior compression
policies treat them as fungible tokens. This paper measures **55
archived coding-agent trajectories** to build the case for
object-aware policies.

### In-depth insights

- Studies two semantically informed strategies: an **object-aware
  compression policy** and a **retrieval-based policy**.
- Two operator-level takeaways:
  1. Calibration gains on one task **may not transfer** to held-out
     tasks — beware of overfitting your memory config to a benchmark.
  2. Equal token budgets **do not imply** equal delivered context or
     equal management cost — a "10 KB budget" comparison is often
     misleading.

## Proof-of-Execution Memory — Defending Against Forged-Reasoning Attacks

- Source: <https://arxiv.org/abs/2608.16032>
- Date: 2026-08-17 (Rahman, Kim — Gyeongsang National University)

### Why it matters for local models

Direct follow-up to July's **FARMA** paper and its **SENTINEL**
defence. The paper's headline result is a demolition of SENTINEL: an
automated attacker that just asks a language model to reword the
forgery **evades SENTINEL on its first try, reducing its protection to
0% on every model tested**. Any local agent that adopted the July
FARMA/SENTINEL guidance needs to look at this immediately.

### In-depth insights

- Attack succeeds **98–100% on GPT-4o and GPT-4o-mini**, **44% on
  Llama-3.1-8B** — the *stronger* model is more vulnerable, because it
  paraphrases more fluently.
- Proposes **Proof-of-Execution Memory**: verify what actually
  happened in the agent's execution history rather than scoring
  entries against a static suspicious-wording list. Positioned as a
  provenance layer under the memory rather than a content filter over
  it.

## Qwen3.8-Max open weights — the new "1M-context on open weights" baseline

- Announcement: Alibaba Qwen released the weights of Qwen3.8-Max as
  **Qwen3.8-2.4T-A95B** on 2026-08-12.
- Reference (secondary):
  <https://www.marktechpost.com/2026/08/03/alibaba-qwen-releases-qwen3-8-max/>

### Why it matters for local models

Together with DeepSeek V4-Pro (GA 2026-08-13, MIT, 1M context, 1.6T
MoE / 49B active) and last cycle's NVIDIA Nemotron 3, there are now
**three open-weights model families with a native 1M context** in
production. Every "our memory framework helps beat 128k context"
argument needs to be re-run against the 1M-context open baseline.

### In-depth insights

- 2.4T MoE, ~95B active parameters per token.
- 1M-token context window (open-weights variant has a native context
  of 262,144 tokens with ~1.01M extensible).
- **Custom Qwen3.8-Max License** — *not* Apache; check the licence
  before commercial use. First time Alibaba has open-sourced a
  Max-class flagship.
- Second-order effect: the Qwen3.8-27B dense sibling shipped
  2026-08-14 with a 262K native context, giving local operators a
  smaller open-weights option in the same family.

## OKF v0.2 — Optional Trust Signals Added

- Version 0.2 published 2026-07-25 (one day after last report).
- Reference (secondary):
  <https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing>

### Why it matters for local models

OKF v0.1 (June 2026) formalised the "LLM Wiki" pattern as a portable
markdown-plus-YAML bundle. v0.2 adds **five optional fields:
provenance, trust, freshness, lifecycle, attestation** — every one of
which lines up with a stage from MemGauge's utility-risk analysis
above. For a local operator, these are the fields to start writing
into your own memory files *now* even if no runtime reads them yet.

### In-depth insights

- **v0.1 bundles remain fully compatible** with a v0.2 reader; no
  breakage.
- **No major AI agent reads OKF bundles natively as a default
  behaviour** as of Sep 2026 — adoption is still early-practitioner.
  Watch for the first framework (Letta / mem0 / MemOS / Cognee) to
  add an OKF importer; that will be the tipping-point signal.
