# LLM Memory — 2026-07-11

## Summary

Between the April 23 report and today, the memory-for-LLMs space has moved on three fronts. First, **evaluation** — BEAM (ICLR 2026, arXiv 2510.27246) is now the reference "beyond context window" benchmark at 1M and 10M tokens, and a wave of diagnostic benchmarks (MemFail, EvoMemBench, StreamMemBench) shifted the conversation from "final accuracy" to failure-mode analysis and streaming/self-evolution. Second, **frameworks** — Mem0 shipped a token-efficient v2 (April 2026 algorithm, June 2026 temporal-reasoning update) that closes most of the historical gap with Zep at ~1/3 the tokens; Letta continued moving off DB-block memory toward git-backed MemFS "context repositories" that fit local CLI workflows. Third, **research** — the ICLR 2026 MemAgents workshop (April 27) surfaced A-MAC (structured admission control) and ALMA (meta-learned memory designs), and the first serious **long-term memory security** survey (arXiv 2604.16548, v2 June 11, 2026) formalized memory as an attack surface. No confirmed Titans/MIRAS follow-up landed in this window; the most-cited critical follow-up ("Titans Revisited") is October 2025 and predates the last report.

## Mem0 Token-Efficient Algorithm v2 (temporal-reasoning update)

- Source: <https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm>, <https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning>, <https://mem0.ai/research>
- Date: 2026-04 (initial algorithm) with a temporal-reasoning follow-up shipped later in 2026-Q2

### Why it matters for local models

Mem0 is Apache-2.0 and runs against any OpenAI-compatible endpoint (Ollama/vLLM/LM Studio), so the algorithmic changes flow directly to self-hosted stacks. The v2 pipeline is a **single-pass ADD-only extraction** — one LLM call per turn instead of the older ADD/UPDATE/DELETE cycle. That's the difference between a memory layer being cheap enough to run on a 7–14B local model or not: the blog reports **~91% latency and ~90% token reduction vs. v1**. It also adds entity-level matching on top of sentence-level retrieval, which matters more on small models whose embeddings are noisier.

### In-depth insights

- Reported scores: **92.5 on LoCoMo, 94.4 on LongMemEval, 64.1/48.6 on BEAM 1M/10M**, at ~7K tokens per retrieval call vs. ~25K+ for full-context baselines.
- Temporal-reasoning gap vs. Zep (which used to lead LongMemEval 63.8 vs. Mem0 v1's 49.0) is now reportedly closed at **93.4** on the same category.
- Improvements on the two most user-relevant categories: **+29.6 points temporal**, **+23.1 points multi-hop** over v1.
- Caveat: numbers are self-reported on Mem0's own benchmark page; independent replication by Maxim ("claimed vs. observed") is more skeptical of the headline figures (<https://www.maximem.ai/blog/state-of-ai-memory-2026-claimed-vs-observed>).

## BEAM benchmark + LIGHT framework (ICLR 2026)

- Source: <https://arxiv.org/abs/2510.27246>, <https://github.com/mohammadtavakoli78/BEAM>, <https://mohammadtavakoli78.github.io/beam-light/>
- Date: ICLR 2026 (presented April/May 2026), arXiv v1 October 2025

### Why it matters for local models

BEAM is the first benchmark that **explicitly tests whether a large context window can substitute for a memory system** at the scale local models can now claim (1M is table stakes for Llama 3.1/DeepSeek/etc. via YaRN or native). Answer: no — even 1M-context models with RAG struggle as dialogue length grows, so a memory layer remains necessary even for open-weight long-context models. The paired LIGHT framework (episodic vector store + working memory + scratchpad) is architecture-agnostic and cheap enough to reproduce on top of a local backbone.

### In-depth insights

- BEAM: 100 conversations, 2,000 validated questions, **1M and 10M token tracks**, 10 categories (preference following, instruction following, information extraction, knowledge update, multi-session reasoning, summarization, temporal reasoning, event ordering, abstention, contradiction resolution).
- LIGHT reports **+3.5% to +12.7% average improvement over the strongest baseline** across backbones. Modest absolute deltas — the paper is more useful as a benchmark contribution than as an SOTA memory system.
- Code released on GitHub under MIT-ish license; benchmark data is available for local reproduction.
- Note: this paper was not covered in the April report despite an October 2025 arXiv date because its ICLR 2026 acceptance and public discussion (Hindsight, Vectorize) landed in Q2 2026.

## Letta Context Repositories / MemFS

- Source: <https://www.letta.com/blog/context-repositories/>, <https://docs.letta.com/letta-code/memfs>, <https://github.com/letta-ai/letta-code>
- Date: 2026-02 announcement; default-on in Letta Code 0.15+ through Q2 2026; core-memory char limits raised in 2026-03-31 v0.16.7

### Why it matters for local models

This is the biggest architectural shift in an open-source memory framework this quarter. Memory blocks are now **markdown files in a git repo on disk**, not rows in a Postgres/SQLite table. Concrete implications for self-hosted setups: (1) the agent uses `bash`/`grep`/standard Unix tools to manage its own memory instead of custom `core_memory_replace` — same tool surface as a local coding agent; (2) subagents get isolated worktrees and merge back through git, which unlocks parallel memory writes without a shared DB; (3) memory is user-inspectable and diff-able, matching how open-weight users already run things.

### In-depth insights

- **Global default context raised from 32K → 128K**; core-memory block char limit raised from 20K → 100K.
- Block-limit validation deprecated — memory can grow freely.
- Migration: `/memfs enable` on existing agents detaches the legacy `memory(...)` tool and syncs blocks into the git-backed FS.
- Trade-off vs. Mem0/Zep: Letta remains a **runtime**, not a drop-in memory library — you commit to running your agent inside Letta. For teams already using Ollama + a custom orchestrator, Mem0 is still the lower-friction path.

## A-MAC — Adaptive Memory Admission Control (MemAgents ICLR 2026)

- Source: <https://arxiv.org/abs/2603.04549>, <https://openreview.net/pdf?id=mmdqUrEY24>
- Date: ICLR 2026 MemAgents workshop (2026-04-27)

### Why it matters for local models

Every mem0/Letta/Zep deployment has to decide "does this turn get written to long-term memory?" — today that decision is either heuristic ("write everything") or opaque (a big LLM call scores it). A-MAC formalizes it as a structured, auditable admission decision with **rule-based features + a small LLM scorer**, which is cheaper on a local backbone and inspectable enough for regulated deployments.

### In-depth insights

- Decomposes memory value into 5 dimensions: **future utility, factual confidence, semantic novelty, temporal recency, content-type prior**.
- Hybrid rule+LLM architecture beats a pure LLM-scoring baseline on accuracy-vs-cost trade-off (workshop paper — full ablation not yet in a longer arXiv version).
- Authors are from Workday AI; not an academic-lab paper, biased toward production-realistic constraints.
- Practical takeaway: even without adopting A-MAC directly, the five-dimension decomposition is a good template to bolt onto an existing mem0/Zep pipeline.

## ALMA — Meta-learned Agentic Memory Designs (MemAgents ICLR 2026)

- Source: <https://arxiv.org/abs/2602.07755>, <https://yimingxiong.me/alma>
- Date: ICLR 2026 MemAgents workshop (2026-04-27); arXiv v1 2026-02

### Why it matters for local models

ALMA searches over memory designs *expressed as executable code*, so the winning design is a runnable Python module you can drop into a local agent — not a paper diagram. Practical for the "which schema should my memory store use?" question that every self-hosted user asks and currently answers by copying whatever Mem0/MemGPT does.

### In-depth insights

- A "Meta Agent" evaluates candidate memory designs (schema + retrieval + update code) on a set of sequential decision-making domains, then keeps the best.
- Reports **beating hand-crafted memory designs across four sequential decision-making domains**; specialization to each domain is automatic.
- Limitation to flag: the search is expensive (many rollouts per candidate) — usable as an offline design-time tool, not something you'd run at inference on a local box.
- License: code available via the author's project page; check individual repo for terms.

## New diagnostic benchmarks: MemFail, EvoMemBench, StreamMemBench

- Source: <https://arxiv.org/abs/2605.26667> (MemFail), <https://arxiv.org/abs/2605.18421> (EvoMemBench), <https://arxiv.org/abs/2606.14571> (StreamMemBench)
- Date: 2026-05 to 2026-06 arXiv posts

### Why it matters for local models

Existing memory benchmarks (LoCoMo, LongMemEval, BEAM) report end-to-end accuracy. These three isolate **where** a memory system breaks, which is the interesting question when you're trying to fit a memory layer on top of a small local backbone whose failure modes are different from GPT-5's. If you're picking between Mem0, Zep, Letta, or MIRIX for a 7–14B local model, these benchmarks give you a per-operation diagnostic rather than a single aggregate number.

### In-depth insights

- **MemFail** (2605.26667): decomposes memory into 3 operations — summarization, storage, retrieval — and provides 5 adversarial datasets each stress-testing one. Useful to answer "is my failure in write-side compression or in retrieval?"
- **EvoMemBench** (2605.18421): axes are **memory scope (in-episode vs. cross-episode)** × **content (knowledge vs. execution)**. Compares 15 memory methods with long-context baselines. Headline finding: **no memory form works consistently across all settings, and long-context baselines remain competitive** — sobering for the "you always need a memory layer" thesis.
- **StreamMemBench** (2606.14571): built on EgoLife egocentric streams; tests **evidence use + feedback incorporation + follow-up reuse** on a two-step task sequence. Eight memory systems evaluated; most fail to convert user feedback into reliable follow-up behavior.
- All three release code/data; useful to run against your own local stack.

## MEMTRACK — Multi-platform state-tracking benchmark

- Source: <https://arxiv.org/abs/2510.01353>, <https://huggingface.co/papers/2510.01353>
- Date: arXiv Oct 2025; NeurIPS 2025 SEA Workshop; discussion picked up in Q2 2026

### Why it matters for local models

The prior report listed "MemTrack" as part of the benchmark landscape without much detail; the full paper is now on HuggingFace and has been referenced in recent framework comparisons. This is the closest thing to a **realistic agent-workflow memory benchmark** — asynchronous events across Slack, Linear, and Git, with conflicts and cross-references. Local-agent teams building coding/office assistants can use it as a more honest evaluation than LongMemEval.

### In-depth insights

- Metrics: **Correctness, Efficiency, Redundancy** (not just QA accuracy).
- Best-performing GPT-5 scores only **60% on Correctness** — huge headroom, and a warning that memory systems tuned for LoCoMo/LongMemEval may generalize poorly to cross-platform state.
- Tests memory acquisition, selection, and conflict resolution across platforms — the "which fact is now stale" problem that Zep/Graphiti's dual-timeline design targets.

## Long-Term Memory Security survey (v2)

- Source: <https://arxiv.org/abs/2604.16548>
- Date: v1 2026-04-17; **v2 2026-06-11**

### Why it matters for local models

A memory layer sitting between an LLM and a persistent store is now writable, cross-session, and propagable — a fundamentally different threat model from stateless RAG. This is the first comprehensive taxonomy of the attack surface, and it matters more for local/open-weight deployments where the user (not a hyperscaler) owns the security stack. Anyone running Mem0/Letta/MIRIX in production should read this.

### In-depth insights

- Frames memory as characterized by three properties: **persistence, statefulness, and propagation** — none of which conventional input-centric LLM security addresses.
- Coverage: attacks (poisoning writes, retrieval hijacking, cross-session leakage), defenses (admission control — links to A-MAC — sandboxing, provenance tracking), and governance across the memory lifecycle.
- v2 (June 11) reportedly extends the defense taxonomy; specific v2 diffs not fully verified.

## MemPalace + critical analysis

- Source: <https://arxiv.org/abs/2604.21284> (critical analysis), MemPalace project (referenced but repo/license not independently verified)
- Date: MemPalace project launched 2026-04-08; critical-analysis paper 2026-04-29

### Why it matters for local models

MemPalace is worth flagging because it claims **170 tokens to recall everything** and **zero LLM calls at write time** — extreme optimization for local/edge deployment where every LLM call costs real latency. The critical-analysis paper is more important than the project itself: it shows the headline **96.6% LongMemEval Recall@5** number is largely attributable to verbatim storage + the default all-MiniLM-L6-v2 embeddings, not the spatial-metaphor architecture. Useful cautionary tale when reading self-reported benchmark leaderboards this quarter.

### In-depth insights

- Architecture: wings (people/projects) → halls (memory types) → rooms (topics) → closets (compressed summaries) → drawers (verbatim originals).
- Reported but not independently verified: 47K GitHub stars in 2 weeks, 96.6% LongMemEval Recall@5.
- Critical paper's actual finding: **verbatim storage + default MiniLM embeddings drive the score**, not the memory-palace metaphor. Generalizable lesson: for retrieval-heavy memory benchmarks, storing raw text and using a decent embedder is a very strong baseline.
- Reported but not yet verified: license or the star-count claims could not be independently confirmed.

## Open questions / follow-ups

- **Titans / MIRAS follow-up** in the April→July window: no confirmed post-April 2026 successor from Google or an obvious independent extension beyond the pre-existing "Titans Revisited" (2510.09551, Oct 2025) reimplementation. Worth re-checking at the next report.
- **MIRIX v2 / open weights**: MIRIX (arXiv 2507.07957, July 2025) has an active GitHub (Mirix-AI/MIRIX) with a Python SDK on PyPI — check for a formal v2 or fine-tuned local-model variant by next quarter.
- **Zep temporal-graph counter-response** to Mem0 v2 closing the LongMemEval gap — any new benchmark or Graphiti release? None confirmed in this window; several third-party 2026 reviews still list Zep as SOC2/HIPAA leader for enterprise but the algorithmic lead is being challenged.
- **BEAM leaderboard beyond LIGHT**: Hindsight claims BEAM SOTA (blog, April 2026); a full comparison against Mem0 v2 and MIRIX on BEAM-10M would be more informative than any single number.
- **EvoMemBench's null finding** — "long-context baselines remain competitive; no memory form dominates" — deserves a direct rebuttal or confirmation from a large-scale reproduction; watch for a follow-up paper in Q3 2026.
- **SSM/persistent-state** for local memory: xLSTM 7B remains the main open-weight SSM candidate but no clean May–July 2026 paper pairs it with an external memory framework surfaced in this cycle. Worth an explicit search next time.
