# LLM Memory — 2026-08-29

## Summary

The 5-week window since 2026-07-25 was heavier on **framework releases and
infrastructure** than on new evaluation papers. The two loudest moves were
**Letta shipping a real Agents SDK** (TypeScript, stateful backends,
MemFS + Dreaming primitives) on 2026-08-17 and **MemOS** completing a
production-quality **DeepSeek Harness plugin** across the v2.0.26–v2.0.32
release train. **Cognee 1.5.0** landed the Ladybug graph adapter and a
Letta/MemGPT/Zep migration path, **supermemory-server** hit 0.0.8 with a
self-hosted license tier, and **LMCache 0.5.4** turned its multi-process
coordinator into a real fleet control plane — matched by an AMD ROCm blog
post that combines LMCache with **4-bit TurboQuant KV** on MI355X.
Google's research blog re-surfaced **Titans + MIRAS** on 2026-08-25 as a
framework for test-time-training memory, without shipping open weights.
On arXiv, a wave of *"post-storage"* memory papers appeared — MemArbiter,
StateAuditor, and dependency-guided rollback all reframe failures as
occurring *after* memories are correctly stored — plus **MemTrapBench**,
which shows that faithfully-stored memories can still degrade reasoning.
Two KV-cache papers (**HiSparse**, **S⁴R**) push sparse-attention serving
past HBM. **NVIDIA Nemotron 3.5 Lightning** (30B MoE / 3B active, 1M
context, hybrid Mamba-Transformer) also lands as a new open-weight
baseline that any local memory stack now competes against. **OKF v0.2**
adds a trust/provenance layer to Google's Open Knowledge Format.

## MemOS v2.0.26–v2.0.32 + DeepSeek Harness plugin

- Source: <https://github.com/MemTensor/MemOS/releases>
- Companion coverage: <https://hindsight.vectorize.io/blog/2026/08/14/deepseek-harness-persistent-memory>
- Dates: 2026-07-31 through 2026-08-28

### Why it matters for local models

MemOS continued its weekly cadence and closed the gap between "memory
OS" and "memory OS with a real agent runtime attached." The
**DeepSeek Harness (DSH) integration**, announced 2026-08-17 and
stabilized across v2.0.16 (local plugin) and v2.0.30/v2.0.32 (core),
lets an open-weight coding-agent harness gain persistent, per-project
memory through a plugin — no fork of DSH is required. For local
deployments this is the first cross-project pairing of MemOS with an
open agent harness rather than a hand-rolled CLI.

### In-depth insights

- **v2.0.32 (2026-08-28)**: DSH memory adapter integration; embedder
  configuration preservation; PID-based lock detection fixes; storage
  index optimization.
- **v2.0.30 (2026-08-14)**: `enable_thinking` support for
  OpenAI-compatible providers; vLLM stream-handling fixes; Windows path
  handling for Hermes.
- **v2.0.17 local plugin (2026-08-24)**: embedding-validation and stale
  lock-detection fixes for large embeddings.
- **v2.0.16 local plugin (2026-08-16)**: DSH long-term memory access
  with automatic recall; `pnpm` autocompletion; native-dependency
  handling on Windows.
- License unchanged (Apache 2.0); paper still <https://arxiv.org/abs/2507.03724>.

## Letta Agents SDK

- Source: <https://www.letta.com/blog/introducing-the-letta-agent-sdk/>
- Repo: <https://github.com/letta-ai/letta-agent-sdk>
- Docs: <https://docs.letta.com/agent-sdk>
- Date: 2026-08-17

### Why it matters for local models

Letta's July release cadence was quiet on the main letta repo (last
tagged release stayed at v0.16.8 from May) but the team pivoted energy
into a **new TypeScript-only Agent SDK** built around stateful agents
as first-class objects — each agent has its own identity, memory,
harness state, and can be resumed on a different machine. Critically
the SDK exposes **`local` and `cloud` state backends**, so a workstation
user can hold the agent state locally while still using MemFS / dreaming
primitives that the platform is standardizing on. This is the first
framework release that treats the "agent object" as portable at the
same level Letta's Agent File (.af) format already did for serialization.

### In-depth insights

- TypeScript-first; Python bindings not yet available.
- Features listed on the blog: **MemFS**, **dreaming**, self-modifying
  harness extensions ("mods"), native channel integrations (Slack,
  Telegram, etc.), pre-optimized toolsets for local computer use.
- Agents can be constructed on different state backends and moved across
  machines while retaining memory and state.
- License and pricing unchanged from previous Letta framework
  (Apache 2.0 for the framework, paid cloud); the SDK repo is a
  separate `letta-agent-sdk` package.
- Note: this is a *layer on top of* the letta agent server, not a
  replacement for it — the older `letta` repo is still what actually
  stores state.

## Cognee v1.5.0 → v1.5.3 (Ladybug graph adapter)

- Source: <https://github.com/topoteretes/cognee/releases>
- Dates: 2026-08-15 (v1.5.0), 2026-08-21 (v1.5.1), 2026-08-22 (v1.5.2), 2026-08-23 (v1.5.3)

### Why it matters for local models

Cognee 1.5 turns the previously optional **Ladybug** graph adapter into
an unconditional runtime dependency and hardens it for large-scale
dataset migrations — set-based fork re-key, chunked queries, batched
rekey/restore. For a local self-hosted deployment this is the version
that finally makes graph memory feel operational at multi-GB corpus
sizes, and it comes with an explicit **migration path from Letta /
MemGPT / Zep** — the first time a mainstream OSS memory framework
ships one-way migration tools targeting its competitors.

### In-depth insights

- **v1.5.0 (2026-08-15)**: LLM temperature and seed controls; Windows
  OpenSSL bundling for Ladybug (`cognee_db_workers/_windows_openssl.py`);
  large-scale migration validation and CI performance tests.
- **v1.5.2 (2026-08-22)**: short-query search-relevance tuning; faster
  ingestion; better error messages; sync-reliability fixes.
- **v1.5.3 (2026-08-23)**: improved ranking + context handling,
  resumable ingestion.
- License unchanged (Apache 2.0). 14 retrieval modes as in v1.4.x.

## supermemory-server 0.0.7 → 0.0.8

- Source: <https://github.com/supermemoryai/supermemory/releases>
- Dates: 2026-08-15 (v0.0.7), 2026-08-17 (v0.0.8)

### Why it matters for local models

The self-hosted supermemory server (Apache 2.0) exited release-candidate
status. v0.0.7 introduces a **self-hosted license tier capped at 10,000
documents** (still free), a local console with memory tracking, ~3-second
boot time, native embeddings restoration, and a diagnostic tool. v0.0.8
follows two days later with an automatic-repair pass to fix a nasty
regression from the 0.0.7-rc line where **upgrading silently wiped search
vectors** — a good example of the "hardening pass" not being cosmetic.
For workstation users this is now the lowest-friction way to stand up a
memory server that is *actually* self-hostable end to end.

### In-depth insights

- Companion tooling published in the same window:
  `claude-supermemory` and `opencode-supermemory` plugins were updated
  on 2026-08-26 and 2026-08-27 respectively.
- License: MIT for the server binary; no restrictions on API calls,
  users, or deployment environments; self-hosted installations
  unrestricted.

## LMCache v0.5.4 + 4-bit KV on AMD MI355X

- Source: <https://github.com/LMCache/LMCache/releases/tag/v0.5.4>
- AMD blog: <https://rocm.blogs.amd.com/software-tools-optimization/4bit-KV-LMcache/README.html>
- Dates: 2026-08-20 (v0.5.4), 2026-08-28 (AMD blog / v0.5.5rc1)

### Why it matters for local models

LMCache's multi-process coordinator was rebuilt as a **fleet-wide
control plane**: a dedicated cache-event ingest layer, unified per-tier
usage management, fleet-metrics export, and CacheBlend lookups that
search fleet-wide rather than locally. Wheels now cover **arm64 /
aarch64 (GB200 / GB300 / Thor / Spark)**, RBLN, and MUSA in addition to
CUDA and ROCm. Combined with the AMD post on 2026-08-28 — **TurboQuant
4-bit KV** offloaded past HBM into CPU DRAM through LMCache, described
as "bit-exact, accuracy-neutral" — the KV cache is now positioned as
the primary persistent-memory substrate for open-weight agent
inference on non-CUDA hardware.

### In-depth insights

- **v0.5.4**: env-var config replaced by explicit CLI flags;
  `lmcache_native` module (with `c_ops` legacy surface removed); lazy
  offload and enqueue-time prefetch off the critical path; substantial
  single-head large-block throughput improvements.
- **v0.5.5rc1 (2026-08-28)**: `--no-warmup` for the `lmcache bench
  engine` CLI; CUDA 12.9 / 13.0, ROCm 7.2 (gfx942, gfx950), Intel XPU
  wheels published the same day.
- AMD post: mixed bf16 + 4-bit cache made safe to offload via a
  layout-aware connector; benchmark focus is context-heavy agentic
  workloads.
- Note: the `-v0.5.4` GitHub release fetch briefly reported a 2024
  date; the release page listing gives 2026-08-20 and the surrounding
  releases (rc5 same day, rc6 through v0.5.5rc1 in Aug) confirm 2026.

### Why it matters for local models

Not a memory system, but the reference open-weight model that every

## Google Research — Titans + MIRAS follow-up blog

- Source: <https://research.google/blog/titans-miras-helping-ai-have-long-term-memory/>
- Date: 2026-08-25
- Related critique paper: <https://arxiv.org/abs/2510.09551>

### Why it matters for local models

Google's first prominent Titans-line update since the January 2025
paper. It reframes Titans as the *architecture* and **MIRAS** as the
theoretical framework unifying online optimization, associative memory,
and architectural design for test-time-training memory. Still **no
official code, no open weights**, and the community reimplementation
(`lucidrains/titans-pytorch`) plus the ICLR-track *Titans Revisited*
paper (2510.09551) remain the closest a local user can get. This is
the paper the previous cycle's *Beyond Perplexity* critique was aimed
at; it also matters because Cognee's 1.5-line and the *Memory for LLMs*
survey both cite the Titans/MIRAS thread as one of the two dominant
frames for LLM memory alongside explicit-memory frameworks.

### In-depth insights

- Blog claims: LMM (Long-Term Memory Module) as a deep, non-linear
  recurrent meta-in-context learner; adaptive "surprise" metric with
  momentum; adaptive forgetting to bound memory.
- No new benchmark numbers in the blog post itself relative to the
  original Titans paper; MIRAS is positioned as a *design theory*
  rather than a new model checkpoint.
- Take with a large grain of salt until code lands; the *Titans
  Revisited* paper (Di Nepi et al., 2510.09551, Oct 2025) already
  showed that the base Titans architecture does not always beat
  established baselines on masked LM, time-series forecasting, and
  recommendation, due to chunking.

## MemArbiter — decision-time memory arbitration

- Source: <https://arxiv.org/abs/2608.02113>
- Date: 2026-08-03

### Why it matters for local models

Formalizes the **"Memory-Action Gap"**: action-relevant information
that has been retrieved correctly still fails to guide the next
decision because it is poorly organized or presented at the wrong time.
MemArbiter re-organizes memory into **five functional Memory Banks**
and combines bank-level demand, item-level relevance, focal-ambient
representations, and a temporal presentation gate. On long-horizon
agent evaluation with an **open-weight action-generation model**, it
reports **82.8%** success at a **500-token** budget and **92.5%** at
**750**, beating the strongest baseline by **+20.9** and **+25.4**
points respectively.

### In-depth insights

- Authors: Jiajun Dong, Yutao Hu, Fengrui Fan, Shihan Dou, Yueming Wu,
  Deqing Zou.
- The framing complements *AutoMem* (arXiv 2607.01224, Stanford,
  2026-07-01) which treats memory management as a trainable
  metamemory skill — MemArbiter is inference-only arbitration on top
  of an existing store, AutoMem trains the memory skill itself.
- No code URL published in the paper text as of the initial arXiv
  drop — treat that as UNVERIFIED until confirmed.

## StateAuditor + Dependency-Guided Rollback — post-storage memory repair

- Sources:
  - StateAuditor: <https://arxiv.org/abs/2608.01619>
  - Dependency-Guided Rollback Repair: <https://arxiv.org/abs/2608.10502>
- Dates: 2026-08-03 and mid-August 2026

### Why it matters for local models

Both papers attack the same class of failure: memory-augmented agents
that *know* a fact has been updated but still act on the stale value.
StateAuditor introduces the **STALE benchmark** (400 scenarios,
50-session histories) and the "Implicit Policy Adaptation (IPA) gap,"
then audits from **stored state → draft** instead of the usual
draft-anchored verification. The rollback-repair paper builds a
**typed memory-to-action graph from runtime provenance**, traces
downstream dependencies, and deactivates unsupported state — instead of
either deleting the source or replaying the full trace. For any local
Letta / MemOS / mem0 deployment that persists memory, these describe
the concrete repair paths you eventually need.

### In-depth insights

- StateAuditor reports **+5.0 pts VTA** over a matched locked
  predecessor on STALE's strict single-query protocol; verified is
  provenance and chronology, not semantic supersession.
- Rollback-repair preserves candidates with independent trusted support
  and only deactivates unsupported state — matters because deleting
  the source leaves derived memories active.
- Both are diagnostic + repair frameworks rather than shipping code
  libraries; expect them to influence 2026-Q4 Letta / mem0 release
  notes.

## HiSparse & S⁴R — sparse-attention KV that finally escapes HBM

- Sources:
  - HiSparse: <https://arxiv.org/abs/2608.07009>
  - S⁴R: <https://arxiv.org/abs/2608.00528>
- Dates: 2026-08-07 (HiSparse), 2026-08-01 (S⁴R)
- HiSparse blog: <https://www.lmsys.org/blog/2026-04-10-sglang-hisparse/>

### Why it matters for local models

Sparse attention (DSA, NSA, Quest) reduces compute but forces the
**entire KV cache to sit in GPU HBM** so any position is still
selectable, which is what actually caps context on a single-GPU box.
**HiSparse** keeps each request's full KV in host memory and gives it a
small fixed-size GPU cache; each layer's top-k selection is resolved
against that cache first, then misses are fetched in one batched host
transfer. It is **indexer-agnostic** — slots under DSA / NSA / Quest
without retraining — and merged upstream in SGLang. **S⁴R** attacks the
same problem from the compression angle, using prompt-aware
initialization to build key/value bases and sparse reconstruction to
retain only informative positions during decoding.

### In-depth insights

- **HiSparse**: up to **4.7× peak generation throughput** on
  long-context workloads while preserving per-token latency and
  reducing TTFT under load; a modest LRU device cache achieves **87%
  device-hit rate** on a LongBench V2 selection trace; evaluated on
  H200, B200, GH200.
- **S⁴R**: up to **5× KV compression** with near full-cache accuracy
  on LongBench and RULER.
- Both are complements to LMCache's 4-bit KV work — LMCache tiers
  compressed KV between memory levels; HiSparse manages hierarchical
  KV within a running sparse-attention engine; S⁴R shrinks what needs
  to be stored in the first place.

## Test-Time Context Distillation (TTCD)

- Source: <https://arxiv.org/abs/2608.01672>
- Date: 2026-08-02

### Why it matters for local models

An explicit **test-time-training** (TTT) method whose objective is
"which of the current context tokens should be retained for future
predictions." A short-window student's hidden state is distilled against
a long-window teacher of the same model; the discrepancy is the
self-supervised signal for the student's fast weights. Directly
relevant to the Titans / MIRAS line — this is a peer-reviewable *TTT
for memory* proposal with an actual reproducible-scale evaluation.

### In-depth insights

- At **760M params**, TTCD more than **doubles IP-TTT** on the RULER
  long-context benchmark, with the gap widening as context length
  grows.
- Applied as continual pre-training to **SmolLM2-360M / 1.7B** and
  **LLaMA-3.1-8B**, improves RULER at 32K and 64K — i.e. plug-in for
  existing transformer weights, not a new architecture.
- Answers the concern that TTT memory papers do not show benefit over
  explicit memory: TTCD's evaluation is on RULER (retrieval-style
  long-context), not perplexity, so the *Beyond Perplexity* critique
  from the previous cycle is at least partly addressed.

## MemTrapBench — cognitive traps in LLM memory use

- Source: <https://arxiv.org/abs/2608.20202>
- Date: 2026-08-20

### Why it matters for local models

The first benchmark to measure how faithfully-stored memories can
**degrade** downstream reasoning by trapping the model in a prior
belief. Two trap types: **Reasoning Fixation** (persistent prior
patterns block a new solution) and **Belief Distortion** (stored
context skews confidence in current reasoning). Result across two
model families and **five representative memory frameworks**: **all
memory strategies underperform the no-memory baseline**, with even
the strongest suffering **>10% drops**. The paper proposes
**AdaptiveMem** as a mitigation.

### In-depth insights

- Concrete example: a 20-turn arithmetic game where the model
  correctly ruled out factorial as needed; on turn 21 with `[0, 2, 2, 8]`
  it needs factorial (`(2^2 - 8)! = 4! = 24`), and the accumulated
  memory of the first 20 turns pins it to the earlier reasoning.
- The stark bottom line ("memory makes things worse") is the strongest
  argument yet for benchmarking any local memory stack **against a
  no-memory baseline** rather than only against other memory
  frameworks.

## SuperLocalMemory 4.0 — governed local-first memory OS

- Source: <https://arxiv.org/abs/2608.08253>
- Code: <https://github.com/qualixar/superlocalmemory>
- Date: 2026-08-11

### Why it matters for local models

An entire local-first memory *operating system* framed for enterprise
compliance: dense-semantic + BM25 + temporal + Hopfield-associative +
spreading-activation retrieval, reciprocal-rank fusion, bi-temporal
recall, multi-scope (personal / shared / global), RBAC, GDPR export /
verified erasure, audit trails, EU AI Act checklist. Ships with three
operating modes: **fully local**, **local with on-device LLM
enrichment**, and **provider-assisted**. Runtime is available through
CLI, MCP, HTTP daemon, dashboard, editor integration, and framework
adapters.

### In-depth insights

- v4 introduces "reliability spine": generation-fenced admission,
  policy registry, verifiable memory transactions with per-projection
  apply-verify.
- **Overhead of the governed write envelope**: 3.522ms p50 / 5.297ms
  p99 vs. 1.835ms / 2.569ms for ungoverned baseline — i.e. **~1.7ms
  p50 / ~2.7ms p99** control-plane cost.
- Sits closer to a *policy layer* than a *retrieval algorithm* — the
  interesting delta over Cognee / MemOS is the compliance surface, not
  raw benchmark scores.

## OKF v0.2 — trust / provenance layer

- Source: <https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf>
- Coverage: <https://www.techwyse.com/news/search-seo/google-open-knowledge-format-v02-trust-signals>
- Date: 2026-07-25

### Why it matters for local models

OKF (v0.1 was in the previous cycle) added five optional fields to the
Markdown-with-YAML-frontmatter spec: **provenance, trust, freshness,
lifecycle, attestation**. Concretely: `sources`, `generated`, `verified`,
`stale_after`, `status`. Only `type` remains required, so v0.1 bundles
stay valid. For local users, this is the missing piece that lets a
hand-curated OKF bundle carry "who wrote this, who checked it, when it
expires" without inventing a bespoke schema — which is what any local
memory framework running against a shared team knowledge base will end
up needing.

### In-depth insights

- Adoption note: as of 2026-08, no major open agent runtime is reading
  OKF bundles natively yet — Cognee's 1.5.x line has migration paths
  from Letta/MemGPT/Zep, but not an OKF ingestor. Practical use today
  is still hand-plumbed.
- License: open specification, vendor-neutral; the reference tools
  (enrichment agent, static HTML visualizer) live in the
  `GoogleCloudPlatform/knowledge-catalog` repo.

## Memory for Large Language Models — architecture-centric survey

- Source: <https://arxiv.org/abs/2607.25380>
- Date: 2026-07-28

### Why it matters for local models

A survey landing exactly on the boundary of this window that proposes a
**three-axis taxonomy**: representation (implicit vs. explicit), update
dynamics (offline vs. online), persistence (short vs. long). This is
useful specifically for arguing about local-model memory choices,
because it cleanly separates KV / activation memory (implicit + short)
from framework memory like MemOS / Letta / mem0 (explicit + long) and
TTT memory like Titans (implicit + online + long) — the axes fall
along exactly the tradeoffs a local deployment has to make.

### In-depth insights

- Authors: Sining Zhoubian, Dan Zhang, Evgeny Kharlamov, Jie Tang
  (Tsinghua / Aalto lineage).
- The survey formalizes memory writing, routing, state transitions,
  and consolidation — vocabulary that maps onto the *post-storage*
  papers (MemArbiter, StateAuditor, MemTrapBench) surfacing this
  cycle.
- Positioned as a reference for the fragmentation between "attention
  as memory" and "explicit store as memory" schools.

## Open questions / follow-ups

- **Titans / MIRAS code**: still no open weights or reference
  implementation from Google despite the 2026-08-25 blog. Track
  whether the paper backing the MIRAS framework lands on arXiv, and
  whether `lucidrains/titans-pytorch` gets updated to reflect the new
  framing.
- **DSH + MemOS in practice**: run the MemOS 2.0.32 local plugin
  against the actual DeepSeek Harness on a workstation and measure
  whether the automatic recall path actually improves task success
  on a real coding-agent workload — vendor claim of "no core changes
  needed" needs an independent check.
- **Letta Agents SDK vs. letta server**: verify whether the new SDK
  can operate against a fully self-hosted letta backend (no cloud) and
  whether MemFS / dreaming primitives are open or gated.
- **MemTrapBench replication**: reproduce on a Qwen3.5-32B and a
  Llama-3.3-70B backbone with MemOS, Letta, mem0, and a plain
  filesystem baseline — the "memory makes things worse" headline is
  the single most important claim of the cycle if it holds up.
- **HiSparse × LMCache**: HiSparse manages sparse-attention KV inside
  the engine, LMCache tiers KV between memory levels — no paper yet
  shows what they do combined. This is the highest-leverage
  reproducibility exercise for a workstation memory report.
- **AgentMemBench / other 2608 benchmarks**: several *"MemBench"*
  papers appeared with 2608.* arXiv IDs but with reported submission
  dates that predate arXiv's numbering (i.e. potentially miscategorized
  or updated). Verify submission dates directly against arXiv metadata
  before citing benchmark numbers in future reports.
- **ByteRover 2.0 (92.2 LoCoMo) / ZeroMemory (96.1 LoCoMo)**: both
  claims surfaced in leaderboard blog posts inside the window but
  without corresponding open papers. Chase down whether either has an
  actual technical writeup or is marketing over an unpublished stack;
  do not cite the numbers standalone.
- **mem0 Strands / DeepSeek plugin design**: check whether "automatic
  recall and injection" is genuinely policy-free or ships with a fixed
  retrieval heuristic that biases evaluation.
