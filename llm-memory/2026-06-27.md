# LLM Memory — 2026-06-27

## Summary

The May–June 2026 window was dominated by new benchmarks and a wave of
"agent-native" memory systems for open-weight models. **LongMemEval-V2**
(May) and **PrecisionMemBench** (May) both argue that the prior generation
of benchmarks measured the wrong thing — V2 shifts evaluation toward
enterprise workflow tasks, while PrecisionMemBench decouples retrieval
precision from generation quality. On the systems side, **MemPalace**
(v3.5.0, MIT, fully local) and **Vestige** (Rust + MCP, FSRS-6 spaced-
repetition) emerged as serious open-weight contenders, while **AtomMem**
(Qwen3-14B fact extractor) hit state-of-the-art LoCoMo numbers using
only a single-GPU LoRA. Production frameworks shipped meaningful upgrades:
**Mem0** added "auto-dream" consolidation in its OpenCode plugin,
**MemOS** introduced Reflect2Evolve and a hook-based plugin system, and
a major systems-characterization paper (Omri et al., arXiv 2606.06448)
gave the first phase-aware profiling harness for ten memory systems.
The throughline: local-first memory is now competitive with hosted
services on the main public benchmarks, and the field is starting to
instrument itself seriously.

## LongMemEval-V2: Evaluating Long-Term Agent Memory Toward Experienced Colleagues

- Source: <https://arxiv.org/abs/2605.12493>
- Code/data: <https://github.com/xiaowu0162/LongMemEval-V2>
- Date: 2026-05-19 (arXiv submission)

### Why it matters for local models

V2 reframes long-term memory evaluation around web/enterprise agent
workflows rather than chat history, raising the bar past the saturated
v1 leaderboard. Because the trajectories are public (HuggingFace
dataset, GitHub repo) and runnable end-to-end, open-weight memory
systems can finally compete on the same axis as proprietary stacks
without an API budget.

### In-depth insights

- 451 manually curated questions paired with up to 500 history
  trajectories (~115M tokens) drawn from WebArena- and ServiceNow-style
  environments.
- Tests five core abilities: static state recall, dynamic state
  tracking, workflow knowledge, environment gotchas, and premise
  awareness.
- Authors: Di Wu, Zixiang Ji, Asmi Kawatkar, Bryan Kwan, Jia-Chen Gu,
  Nanyun Peng, Kai-Wei Chang (UCLA + collaborators).
- Original LongMemEval was ICLR 2025; V2 is the explicit successor.

## Structured Belief State and PrecisionMemBench

- Source: <https://arxiv.org/abs/2605.11325>
- Date: 2026-05-16 (arXiv)

### Why it matters for local models

Argues that LoCoMo / LongMemEval conflate retrieval quality with
generative-model quality and proposes the first precision-only
benchmark that you can run without an LLM at all. Critical for
local-stack tuning where you want to isolate the embedding /
retriever from a weaker open-weight generator.

### In-depth insights

- 89 hand-crafted cases probing scope, mutation, and isolation
  assertions.
- Reports that mainstream memory baselines hit mean retrieval
  precision of only **0.05–0.08** on cases that reference their own
  extractions — i.e. less than 1 retrieval in 10 is correct on
  precision-tight queries.
- Authors also ship "Tenure," a local-first structured belief store
  using multi-path BM25 with analyzer asymmetry, differential
  boosting, and hard scope isolation; passes 89/89 with mean
  precision 1.0 and sub-15ms retrieval.
- Local-first by design (no LLM required for the retriever).

## Beyond a Million Tokens: BEAM Benchmark + LIGHT Framework (ICLR 2026)

- Source: <https://arxiv.org/abs/2510.27246>
- Project page: <https://mohammadtavakoli78.github.io/beam-light/>
- Code: <https://github.com/mohammadtavakoli78/BEAM>
- Date: ICLR 2026 main conference; project page refreshed for the
  April 26–27 workshop window and active into May/June.

### Why it matters for local models

BEAM is the first public benchmark that pushes coherent dialogues to
**10M tokens** — beyond the 1M context limits of most open-weight
models — forcing real memory systems instead of long-context tricks.
LIGHT is a fully open cognitive-inspired framework that gives a clean
baseline you can run on Llama / Qwen.

### In-depth insights

- 100 conversations across 128K / 500K / 1M / 10M token tiers, 2,000
  validated probing questions across ten memory abilities (information
  extraction, multi-hop reasoning, knowledge update, temporal
  reasoning, abstention, contradiction resolution, event ordering,
  instruction following, preference following, summarization).
- LIGHT decomposes memory into episodic store, working memory, and a
  scratchpad; reports 3.50%–12.69% average improvement over strong
  baselines.
- Code MIT, dataset CC BY-SA 4.0.

## MemPalace v3.5.0 — Local-First Verbatim Memory

- Source: <https://github.com/MemPalace/mempalace>
- Date: v3.4.0 on 2026-06-06; v3.5.0 on 2026-06-23
- License: MIT

### Why it matters for local models

100% local stack (ChromaDB + SQLite + Embedding-Gemma-300M),
MCP-compatible, and on the published numbers sits at or near the top
of LongMemEval — explicitly without any closed API. The opinionated
thesis ("verbatim storage beats fact extraction") is now a serious
counterpoint to Mem0 / MAGMA-style extraction-first memory.

### In-depth insights

- Storage is the "palace" metaphor (wings → halls → rooms / drawers)
  over ChromaDB; pluggable backends include SQLite, Qdrant, pgvector.
- Reported scores (June): **96.6% R@5** on LongMemEval (raw semantic
  search baseline, no LLM), **98.4% R@5** on a held-out 450-question
  split (hybrid v4), **88.9% R@10** on LoCoMo, **92.9%** on
  ConvoMem, **80.3% R@5** on MemBench.
- Authors flag honestly that the 100% LongMemEval number tuned on
  three failed questions and call out the 98.4% held-out as the
  "honest publishable claim."
- Ships **35 MCP tools** and auto-save hooks for Claude Code, Cursor,
  and Codex CLI.

## Vestige — Cognitive-Memory MCP Server (Rust, FSRS-6)

- Source: <https://github.com/samvallad33/vestige>
- Date: first public release late April 2026; CHANGELOG hotfix
  2026-05-01, ongoing 2.x releases through June.

### Why it matters for local models

A single ~22 MB Rust binary with RocksDB persistence and zero
external LLM dependencies — literally a single-file memory layer
that any local model with MCP support (Claude Code, Cursor, VS Code,
JetBrains, Xcode) can plug into. Demonstrates that the
"memory-as-MCP-service" pattern is now viable in low-resource
environments.

### In-depth insights

- Memory model borrows from cognitive neuroscience: FSRS-6 spaced
  repetition, prediction-error gating, synaptic tagging, spreading
  activation, decay-weighted vector recall.
- Hybrid BM25 + HNSW retrieval, 83 MCP tools, knowledge-graph layer,
  3D dashboard for inspecting activation.
- Reports **87.8% on LoCoMo** (community-tracked; needs independent
  verification — no peer-reviewed paper yet).
- 2.1.1 added portable export / import preserving memory IDs, FSRS
  state, graph edges, suppression state, audit rows, and embedding
  blobs — important for self-hosters.

## AtomMem: Atomic-Fact Memory with a Qwen3-14B Extractor

- Source: <https://arxiv.org/abs/2606.19847>
- Code: <https://github.com/MINE-USTC/AtomMem>
- Date: 2026-06-25 (arXiv)

### Why it matters for local models

Explicitly built on open weights — a Qwen3-14B fact extractor LoRA-
tuned on a single A100. The whole pipeline is reproducible without
API calls, and it claims state-of-the-art LoCoMo numbers vs.
closed-stack baselines.

### In-depth insights

- A "Fact Executor" distills dialogue into atomic facts, then
  organizes them into hierarchical event structures plus temporal
  user profiles.
- Retrieval activates an associative memory graph to stitch
  fragmented memories together.
- On LoCoMo Multi-Hop and Temporal tasks, AtomMem improves J-score
  by **+5.5 and +31.1** respectively over LightMem, the strongest
  prior baseline; on Open Domain, J-score **64.58 vs Mem0's 54.17**.
- Caveat: do not confuse with a separate similarly-named paper
  (arXiv 2601.08323) using POMDP / GRPO framing.

## Agent Memory: Characterization and System Implications of Stateful Long-Horizon Workloads

- Source: <https://arxiv.org/abs/2606.06448>
- Date: 2026-06-04 (arXiv)

### Why it matters for local models

First serious systems-characterization paper for agent memory — it
builds a phase-aware profiling harness that attributes cost to
construction, retrieval, and generation across ten memory systems.
For anyone running a local memory stack on a single GPU, this is the
literature's first concrete answer to "where does my latency and
token budget actually go?"

### In-depth insights

- Proposes a four-axis taxonomy classifying memory systems across flat
  retrieval, LLM-mediated extraction, consolidating fact stores, and
  agentic control flows.
- Characterizes ten representative systems across two benchmark
  suites and shows how design choices shift cost between write and
  read paths.
- Authors: Yasmine Omri, Ziyu Gan, Zachary Broveak, Robin Geens et al.
  (Georgia Tech systems group, as reported by alphaxiv).

## Are We Ready For An Agent-Native Memory System?

- Source: <https://arxiv.org/abs/2606.24775>
- Date: 2026-06-23 (arXiv)

### Why it matters for local models

A position-plus-empirical paper from the MemOS / MemTensor group
that pushes the field to treat agent memory as a full data
management system (storage, retrieval, update, consolidation,
lifecycle) rather than a glorified RAG cache. Directly relevant
because MemOS is one of the most active open-weight memory OSes.

### In-depth insights

- Decomposes agent memory into four core modules: representation /
  storage, extraction, retrieval / routing, maintenance — and
  evaluates each across cost, robustness under dynamic knowledge
  updates, and architectural trade-offs.
- Authors span Shanghai Jiao Tong University, Tsinghua, and
  MemTensor (the MemOS team).
- Frames the open challenges: cross-module governance, update
  consistency, and benchmark gaps.

## Mem0 v2.0.6–v2.0.8 + OpenCode Plugin (Auto-Dream Consolidation)

- Source: <https://github.com/mem0ai/mem0/releases>
- Plugin: mem0-opencode-plugin v0.2.0 (2026-06-17)
- Date: 2026-06-13 → 2026-06-24 (rolling)

### Why it matters for local models

Mem0 is one of the most widely deployed open-source memory layers;
the v0.2.0 OpenCode plugin is the first time it ships native
"auto-dream" memory consolidation with configurable gates as a
first-class feature, plus per-call and persistent memory scope
management — useful for local-first coding agents.

### In-depth insights

- SDK adds Gemini-via-Vertex provider, batched embeddings across
  five embedders (`embed_batch`), fixes for Anthropic `tool_choice`
  format and tool response parsing, malformed `image_url` handling,
  race-condition fixes in async memory reset / deletion, and a
  CVE-2026-12143 form-data bump.
- CLI v0.2.8 closes a telemetry leak that was passing the Mem0 API
  key to child processes via argv.
- Per Mem0's own May report, the platform algorithm hits **92.5% on
  LoCoMo** and **94.4% on LongMemEval** at <7K tokens per retrieval
  call (down from 25K+ for full-context baselines).

## MemOS v2.0.15–v2.0.20 — Reflect2Evolve, Hook-Based Plugin System

- Source: <https://github.com/MemTensor/MemOS/releases>
- Date: v2.0.15 2026-05-11; v2.0.17 2026-05-26; v2.0.19 mid-June;
  v2.0.20 2026-06-18.

### Why it matters for local models

MemOS positions itself as a self-evolving memory OS for LLMs and
agents with ultra-persistent memory, hybrid retrieval, and cross-task
skill reuse (reported 35.24% token savings). The May / June releases
introduce a real plugin architecture and self-evolution controls —
important for local stacks that need extensibility without forking
the core.

### In-depth insights

- v2.0.15 ships a hook-based plugin system and the "Reflect2Evolve"
  architecture for memos-local-plugin.
- v2.0.17 adds a "lightweight memory mode," memory self-evolution
  controls, OpenClaw memory context preservation, and Windows
  installer improvements.
- v2.0.20 (June 18) adds search-pipeline hooks for context
  rendering.
- The MemOS team is the same group behind the "Are We Ready For An
  Agent-Native Memory System?" paper above.

## Open questions / follow-ups

- ICLR 2026 MemAgents workshop accepted-papers list is paywalled
  behind OpenReview; worth a manual pass to pick up workshop-only
  contributions.
- MemPalace's 96.6% LongMemEval number is reproducible from the raw
  verbatim baseline, but reproductions on Qwen3 vs. Llama3 backbones
  are still scarce — useful to bench against a fixed local model
  next cycle.
- Vestige's claimed 87.8% LoCoMo is community-reported; no peer-
  reviewed paper yet — needs independent verification.
- BEAM's 10M-token tier is hard to run on any single open-weight
  model today; check whether anyone has shipped a hierarchical-
  memory baseline that actually closes the gap rather than just
  truncating.
- "From Storage to Experience" (arXiv 2605.06716) survey wasn't
  included above because it's a survey, but it's the best entry
  point for newcomers; companion repo
  `FeishuLuo/Evolving-LLM-Agent-Memory-Survey`.
- Confirm whether Letta's slow May–June release cadence (only
  v0.16.8 on May 14) reflects a strategic pause or unobserved
  internal-branch development; worth checking commit activity
  directly.
