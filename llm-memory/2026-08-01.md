# LLM Memory — 2026-08-01

## Summary

Papers this week continued the "memory as filesystem" thread that Anthropic's memory tool and Claude Code popularized: a 59-page systematic study from UIUC/UCSD/Adobe (2607.26637, Jul 29) puts the pattern on formal footing, and CMU+Meta's ACM (2607.23809, Jul 26) adds agent-driven compression+offload primitives on top of it. On the architecture side, CoMem (2607.28263) shows unbounded-context memory by writing chunks only through the middle transformer layers and recomputing the top; a Tsinghua/Bosch/Oxford team also dropped a 20-page taxonomy survey (2607.25380). Framework-side, Cognee shipped v1.4.1, MemOS shipped v2.0.27 plus two OpenClaw local-plugin bumps, mem0 shipped Python v2.0.14 (Oracle AI Vector Search) and Node v3.1.2, Graphiti shipped v0.29.3 (FalkorDB fixes), letta-code cut ten releases culminating in v0.30.0, and LMCache added CUDA 12.9/13.0 nightlies and an operator patch. Exabase claimed BEAM SOTA at all three scales (100K/1M/10M) using Gemini 3 Flash. No confirmed movement on Anthropic Dreaming, OKF, or the FARMA/SENTINEL security thread this week.

## Filesystem-Based Memory for LLM Agents: Organization, Evolution, and Sustainability

- Source: <https://arxiv.org/abs/2607.26637>
- Date: 2026-07-29

### Why it matters for local models

This is the first systematic study of the "directory of markdown files that the agent reads/writes itself" pattern that Anthropic's memory tool, Claude Code, and the OKF spec all converge on. For local-model deployments it is directly usable: the memory substrate is the filesystem, the interface is generic file tools, and no bespoke vector store, embedding model, or SDK is on the critical path. It also formalizes something local-agent builders have been doing ad hoc — unifying declarative memory and reusable "skills" in the same store — which matters when a small local model has to reason about which of its own past notes to trust as an organized store grows and rots.

### In-depth insights

Sizhe Zhou, Sheldon Yu, Hui Wei, Junda Wu, Siru Ouyang, Yizhu Jiao, Shijia Pan, Julian McAuley, Yu Zhang, Tong Yu, Jiawei Han (UIUC/UCSD/Adobe collab per author roster). 59 pages, 12 figures, 18 tables. Formalizes filesystem memory as three cooperating agents around one memory FS: a management agent that integrates/organizes incoming content, a search agent that answers queries with cited sources, and an execution agent that supplies trajectories distilled into skills. Explicitly targets the two "unquestioned" defaults in prior memory work: that an agent can keep a growing store organized as memories accumulate/conflict/stale, and that this organization actually pays. Evaluation varies memory shape (agent-organized hierarchy, verbatim dump, chunk retrieval), stream scale, and tool harness across long-conversation benchmarks and embodied tasks. License/code release: not confirmable from primary source in this environment (arxiv.org blocked here); arXiv perpetual non-exclusive license applies by default.

## ACM: Agentic Context Management for Long Horizon Tasks

- Source: <https://arxiv.org/abs/2607.23809>
- Date: 2026-07-26

### Why it matters for local models

Small local models hit context limits fast, and the usual "compress when you hit N tokens" trigger fires for reasons unrelated to what the agent is currently doing — throwing away exactly the wrong content. ACM hands the agent purpose-built context-editing tools so it, not a scheduler, decides when to compress and what to offload to an external memory store. That is the right primitive for a 7-14B local model that has 32-128K of window and needs to run for hours without losing coherence.

### In-depth insights

CMU + Meta. Distinct paper from the same-week Maximem preprint 2607.21503 that also uses the "ACM" name (Jul 23). Approach: purpose-built context-editing tools give the agent explicit compress/offload/query actions; discarded content lands in an external memory store and is re-queried on demand. Reports a 27% relative gain on BrowseComp-Plus and claims the resulting configuration "gets close to open-source models 40x larger" (numbers relayed via community write-ups; not verified against the PDF from this environment). Lowers peak token pressure and produces more consistent runs across independent trials. License/code release status not confirmed from primary source.

## Understanding Is Done Early: A Depth Division of Labor in LLMs (CoMem)

- Source: <https://arxiv.org/abs/2607.28263>
- Date: 2026-07-30 (approx., from arXiv ID)

### Why it matters for local models

CoMem is a genuinely local-friendly recipe: freeze a Qwen3-8B base, train a rank-32 self-distillation LoRA on plain PG-19, and you get unbounded-context memory where model-side read compute and memory are independent of stored-context length. On an H20 at 128K it uses 18.26 GB vs 89.36 GB for full-context KV, with a 7.83x prefill speedup — numbers that fit a serious workstation and beat KV-compression tricks that hurt accuracy.

### In-depth insights

Observation: transformer depth is not used uniformly — lower/middle layers build semantic representations while upper layers specialize for prediction. CoMem (Comprehension Memory) writes each context chunk only through an intermediate layer, caches residual states, and recomputes the query-conditioned upper layers over a retrieved pack. Benchmarks on continued-trained Qwen3-8B under a unified chat-template-free protocol: 97.05 on RULER, 38.27 on LoCoMo vs 34.59 for full-context KV-Direct. 19 pages, 4 figures, 27 tables; adapter-free arm reported separately. License/code release not confirmed from primary source.

## Memory for Large Language Models (survey)

- Source: <https://arxiv.org/abs/2607.25380>
- Date: 2026-07-28

### Why it matters for local models

This is the first survey since the earlier "From Storage to Experience" one (previously covered) that takes an architecture-centric rather than agent-centric view. That framing is more useful for local-model work because it treats KV/attention, SSM state, LoRA-style parametric adaptation, and external lookup as instances of one design space rather than as separate ecosystems.

### In-depth insights

Sining Zhoubian, Dan Zhang, Evgeny Kharlamov, Jie Tang. 20 pages, 4 figures. Framework has three orthogonal axes: representation (implicit vs explicit), update dynamics (offline vs online), persistence (short-term vs long-term). Further formalizes the granular mechanisms for memory writing, routing, state transitions, and consolidation. Complements — rather than duplicates — the March 2026 "Memory for Autonomous LLM Agents" survey and the May 2026 "From Storage to Experience" survey by staying closer to the model-architecture layer. License unconfirmed from primary source.

## Exabase M-1 — SOTA on BEAM at every scale

- Source: <https://exabase.io/blog/exabase-m1-achieves-state-of-the-art-on-beam-benchmark> (announcement mirrored at <https://www.hpcwire.com/aiwire/2026/07/28/exabase-reports-state-of-the-art-results-on-beam-memory-benchmark/>)
- Date: 2026-07-28

### Why it matters for local models

Not directly local — M-1 is closed and runs on Gemini 3 Flash — but the result is a useful ceiling to compare local memory stacks against, and it shows the retrieval algorithm matters more than the LLM: they beat every system that used Gemini 3 Pro. The BEAM benchmark itself (Beyond a Million Tokens, ICLR 2026) is open and is now the de facto multi-scale conversational-memory benchmark that any local memory framework should be reporting against.

### In-depth insights

Closed source; produced by Exabase (the data layer behind the Fabric personal-AI workspace, ~300K users). BEAM scores: 76.9% at 100K tokens, 75.0% at 1M, 68.0% at 10M — highest reported at every scale. Next-best (Hindsight) scored 73.4 / 73.9 / 64.1; Honcho scored 63.0 / 63.1 / 40.6. M-1 also used ~20% fewer tokens per query than the next-best system. Uses Gemini 3 Flash rather than Gemini 3 Pro. Only system currently claiming SOTA on both LongMemEval (115K) and BEAM (10M). No weights, no code released.
