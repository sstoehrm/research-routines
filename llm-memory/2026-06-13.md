# LLM Memory — 2026-06-13

## Summary

Since the April report the field has consolidated around two practical
patterns. First, **filesystem-backed memory for coding agents** moved
from a curiosity (Letta's "is a filesystem all you need?" post) to a
shipped product: Letta Code launched April 6 with git-backed
`MemFS`/Context Repositories, and the same idea shows up independently
in HORMA (arXiv 2606.11680, 77.8% token reduction) and AgentRunbook-C
(72.5% on the new LongMemEval-V2). Second, **test-time training as
memory** stopped being a Google-only story: In-Place Test-Time Training
was accepted as an Oral at ICLR 2026 with a 4B model handling 128K
contexts, NVIDIA published a follow-up TTT-E2E framing, and Tsinghua's
MemoPilot (arXiv 2606.08656) trains the memory-update policy itself
with multi-turn GRPO. The ICLR 2026 MemAgents workshop happened (Rio,
April 23–27) with 110+ submissions — the formal accepted-paper list
is not yet centrally indexed, but the headline Oral was MemAgent
(8K→3.5M extrapolation, >95% on 512K NIAH). On the evaluation side,
LongMemEval got a V2 aimed at web-agent "experienced colleague"
scenarios, GroupMemBench targets multi-party conversation memory, and
"Anatomy of Agentic Memory" (arXiv 2602.19320) documents that
benchmark/backbone variance still dominates framework deltas. New
attack surfaces — sleeper memory poisoning and MemPoison — appeared
fast enough that OWASP shipped an Agent Memory Guard reference
implementation on June 1.

## ICLR 2026 MemAgents Workshop — outcome

- Date: April 23–27, 2026 (co-located with ICLR 2026, Rio de Janeiro).
  Notification was March 1; the previous report flagged this as

### Why it matters for local models

This is the central venue where open-source memory frameworks publish
next to academic work. The mix of submissions and keynote speakers is
the best single signal of what to reproduce on Qwen/Llama backbones
next quarter.

### In-depth insights

- ~110+ submissions, of which a fraction were oral/poster — the
  workshop organisers report this but a single centralized accepted-
  papers page is not yet linked from the workshop site (verified by
  search; OpenReview group page is gated). Papers that explicitly
  list "Published at the ICLR 2026 Workshop MemAgent" on arXiv
  include 2603.04549 and 2603.07670 (the "Memory for Autonomous LLM
  Agents" survey already covered in the April report).
- Keynotes (per MCML / workshop site): Volker Tresp, Chelsea Finn,
  Jeff Clune, Mengye Ren, Aditi Raghunathan, Weiwen Liu, Fred Sala,
  Jeff Pan. Raghunathan's talk previewed "Memorization Sinks" and
  "Natively Unlearnable LLMs" — a parametric-memory thread that maps
  onto the In-Place TTT and MeMo items below.
- A separate ICLR 2026 *main-track* Oral, also confusingly named
  **MemAgent** (Yu et al.), reports extrapolation from 8K training
  context to 3.5M-token QA with <10% loss and >95% on 512K NIAH by
  extending DAPO to optimise the memory-update policy. Source:
  <https://iclr.cc/virtual/2026/oral/10007826>. This is the strongest
  long-context-via-memory result published this cycle.

## In-Place Test-Time Training (In-Place TTT) — ICLR 2026 Oral

- Source: <https://arxiv.org/abs/2604.06169>,
  <https://openreview.net/forum?id=dTWfCLSoyl>,
  <https://huggingface.co/papers/2604.06169>
- Date: paper April 2026, ICLR 2026 Oral acceptance announced April

### Why it matters for local models

The cleanest "memory as fast weights" recipe that works *without
adding modules* to an existing decoder. The MLP final-projection
matrices are treated as adaptable fast weights and updated
chunk-wise during inference; that means an existing Qwen/Llama
checkpoint can in principle be retrofitted. The authors demonstrate
the recipe on a 4B model with 128K context.

### In-depth insights

- Replaces the generic reconstruction objective used by most TTT
  variants with a Next-Token-Prediction-aligned objective; the
  authors argue this is what made earlier LLM TTT attempts fail.
- Chunk-wise update mechanism is designed to be compatible with
  context parallelism, so it can ride existing long-context serving
  setups.
- Limitations called out by the authors: optional but recommended
  pretraining for best results; gains evaluated at 4B scale (not yet
  shown for 70B+); no public numbers yet on whether the fast-weight
  updates persist across sessions or are reset per request — which
  is the real "memory" question.

## NVIDIA TTT-E2E and "Context as Training Data"

- Source: <https://developer.nvidia.com/blog/reimagining-llm-memory-using-context-as-training-data-unlocks-models-that-learn-at-test-time>
- Date: April 2026 series, follow-up to the original post covered in
  the previous report.

### Why it matters for local models

NVIDIA's framing converges with In-Place TTT: compress the context
into the weights via next-token prediction during inference. The
follow-up post (linked from the NVIDIA Research tag pages) explicitly
claims "no performance wall observed" as context length scales,
which is the headline they want for selling H/B-series inference
hardware — but the architectural prescription is open enough that
llama.cpp / vLLM forks can implement it.

### In-depth insights

- TTT-E2E is described as the first method that scales monotonically
  with context length in their experiments. Concrete benchmark
  numbers are not in the blog post — flagged as **unverified** until
  a paper is released.
- Separately at CES 2026 NVIDIA announced **Inference Context Memory
  Storage Platform (ICMSP)** built on BlueField-4, pushing KV cache
  to NVMe with up to 5× claimed efficiency and 5× tokens/sec gains.
  Hardware-only, not directly actionable for local single-GPU setups
  but relevant as the commercial story behind why everyone is
  reframing memory as a storage tier.

## MemoPilot: RL over Memory Updates

- Source: <https://arxiv.org/abs/2606.08656>
- Date: arXiv June 11, 2026.

### Why it matters for local models

Frames the memory-update *policy* as an RL problem and learns it with
multi-turn GRPO around a *frozen* base LLM. That makes it directly
applicable on top of any open-weight model without touching the
backbone.

### In-depth insights

- Casts memory updates as a multi-turn decision problem, optimised
  end-to-end with multi-turn GRPO.
- Introduces turn-wise reward signals and context-independent,
  turn-level advantage estimation, which the authors argue is what
  stabilises training over long horizons.
- Concrete benchmark deltas vs. heuristic-memory baselines are
  reported in the paper but were not visible in the abstract I could
  retrieve — flagged as **unverified** until the PDF is read.

## MeMo: Memory as a Model

- Source: <https://arxiv.org/abs/2605.15156>,
  <https://venturebeat.com/orchestration/memo-memory-model-teams-upgrade-llm-without-retraining>
- Date: arXiv May 20, 2026.

### Why it matters for local models

Splits the system into a small trainable **Memory model** and a
frozen **Executive** LLM. The Executive talks to the Memory model
through a structured multi-turn protocol; no LLM weights or logits
are needed. That makes the recipe usable with closed APIs *and*
local open-weight models without retraining the base.

### In-depth insights

- Training: a frozen Generator converts a target corpus into a
  reflection-QA dataset (extract, consolidate, verify, surface
  entities, cross-document synthesise) used to fit the Memory model.
- Inference cost is independent of corpus size — a real advantage
  over naive RAG when the corpus grows.
- Claimed ~26% performance jump on a knowledge-update task vs.
  baseline (VentureBeat coverage; primary numbers should be
  double-checked against the paper before quoting).

## HORMA: Hierarchical Organize-and-Retrieve Memory Agent

- Source: <https://arxiv.org/abs/2606.11680>
- Date: arXiv June 10, 2026.

### Why it matters for local models

Concrete realisation of the "filesystem-as-memory" idea: a
Hierarchical Management Agent builds a directory of linked notes,
and a Hierarchical Retrieval Agent navigates with Bash/terminal
actions. Maps cleanly onto an existing local-shell agent harness
(llama.cpp + MCP shell, Letta Code, etc.).

### In-depth insights

- Decomposes working memory into structured construction and
  navigation-based retrieval, using recursive skill refinement.
- Reports up to **77.83% token reduction** versus a context-stuffing
  baseline at comparable reasoning quality.
- Tasks evaluated are long-horizon agentic; specific benchmark
  identities and absolute scores are in the PDF (not extracted here).

## TriMem: Beyond Atomic Facts in Lifelong Memory

- Source: <https://arxiv.org/abs/2605.19952>,
  <https://github.com/tmlr-group/TriMem>,
  <https://tmlr-trimem.github.io/>
- Date: arXiv May 19, 2026. Code released.

### Why it matters for local models

Compares against Mem0, MemoryOS, A-Mem, LightMem, SimpleMem and
xMemory on LoCoMo and PerLTQA across multiple LLM backbones. This is
one of the few new memory papers that publishes apples-to-apples
deltas against the actual frameworks people deploy.

### In-depth insights

- Three coexisting representation granularities: raw dialogue
  segments (storage fidelity), atomic facts (efficient retrieval),
  and synthesised profiles (deep reasoning over scattered facts).
- Uses TextGrad-based prompt optimisation to evolve the extraction
  and profiling prompts — no parameter updates required, so it works
  with any frozen open-weight backbone.
- Explicitly addresses the failure mode the April-report meta-
  critique flagged: fact-centric memory discards fine-grained
  details and breaks on deep reasoning over scattered facts.

## LongMemEval-V2: Memory Toward Experienced Colleagues

- Source: <https://arxiv.org/abs/2605.12493>,
  <https://xiaowu0162.github.io/longmemeval-v2/>,
  <https://github.com/xiaowu0162/LongMemEval-V2>
- Date: arXiv May 12, 2026. Dataset on HuggingFace.

### Why it matters for local models

The previous LongMemEval (~115K tokens / question) was already strong
but framed as a chat-history benchmark. V2 reframes the task as *web
agents acquiring environment-specific experience*, which is much
closer to the real coding/agent workflows people want to run locally.

### In-depth insights

- 451 manually curated questions, paired with histories of up to
  **500 trajectories and 115M tokens** — i.e., the "M" regime that
  breaks naive context stuffing.
- Five abilities: static state recall, dynamic state tracking,
  workflow knowledge, environment gotchas, premise awareness.
- The paper introduces two memory methods as baselines:
  AgentRunbook-R (RAG-based, knowledge pools for raw states /
  events / strategy notes) and **AgentRunbook-C** (trajectories as
  files + a coding agent in a sandbox), with C scoring **72.5%
  average accuracy** vs. RAG baseline 48.5% and off-the-shelf coding
  agent 69.3%.
- Latency cost of AgentRunbook-C is high; the authors explicitly
  frame their contribution as advancing the accuracy/latency Pareto
  frontier rather than dominating it.

## GroupMemBench: Multi-Party Conversation Memory

- Source: <https://arxiv.org/abs/2605.14498>
- Date: arXiv May 14, 2026.

### Why it matters for local models

Closes a real gap: every framework people currently benchmark
(Letta, mem0, Zep, MemOS) assumes a single user. GroupMemBench
forces multi-user belief tracking and audience-adapted output.

### In-depth insights

- Three properties the benchmark exposes: (i) group dynamics beyond
  concatenated 1:1 chats; (ii) speaker-grounded belief tracking with
  per-user memory; (iii) audience-adapted language via Theory-of-
  Mind shifts.
- Uses a graph-grounded synthesis pipeline to produce multi-party
  conversations with controllable reply structure and per-user
  personas.
- No leaderboard numbers from existing frameworks have been widely
  circulated yet — this is one to watch for the next cycle.

## "Anatomy of Agentic Memory" — Empirical Audit

- Source: <https://arxiv.org/abs/2602.19320>,
  <https://www.alphaxiv.org/overview/2602.19320>
- Date: arXiv February 22, 2026 (so technically pre-dates the last
  report, but the follow-up empirical analyses landed in May; flagged
  here because it's now the most-cited grounding for "framework
  deltas are smaller than backbone deltas").

### Why it matters for local models

Reinforces and quantifies the meta-critique in the previous report:
backbone choice dominates framework choice, and most benchmarks
saturate. If you're a local-model practitioner trying to pick a
memory stack, this paper is the argument for "start with a strong
backbone, don't over-index on framework benchmarks."

### In-depth insights

- Taxonomy: Lightweight Semantic, Entity-Centric/Personalized,
  Episodic/Reflective, Structured/Hierarchical.
- Pain points called out: benchmark saturation; metric validity and
  LLM-judge sensitivity; backbone-dependent accuracy; latency and
  throughput overhead of memory maintenance is usually unreported.

## Externalization in LLM Agents — Memory + Skills + Protocols

- Source: <https://arxiv.org/abs/2604.08224>,
  <https://www.alphaxiv.org/overview/2604.08224>
- Date: arXiv April 9, 2026. 54 pages.

### Why it matters for local models

Useful framing document: argues that modern agent capability comes
from externalising state (memory), procedure (skills), and
interaction (protocols), with "harness engineering" as the
coordination layer. Directly relevant to anyone building on
llama.cpp / Ollama / vLLM where the harness *is* the product.

### In-depth insights

- Historical progression: weights → context → harness.
- Treats memory, skills, and protocols as three coupled but distinct
  forms of externalisation; argues harness engineering is what
  glues them together in deployed systems.
- Not novel as architecture; valuable as a vocabulary for taxonomies
  in future work.

## Letta Code (app) and Context Repositories

- Source: <https://www.letta.com/blog/introducing-the-letta-code-app>,
  <https://www.letta.com/blog/context-repositories/>,
  <https://docs.letta.com/letta-code/memfs/>,
  <https://github.com/letta-ai/letta-code>,
  <https://github.com/letta-ai/letta>
- Date: Letta Code app launched **April 6, 2026**; Context
  Repositories architecture introduced February 12, 2026; latest
  Letta core release v0.16.8 May 14, 2026.

### Why it matters for local models

Letta Code runs locally and decouples agent memory/identity from the
model provider — you can swap the underlying model mid-session and
keep memory. Memory lives as a git repository of markdown files
under `~/.letta/lc-local-backend/memfs/<agent-id>/memory`, so any
local backend (Ollama, llama.cpp, vLLM) plus any editor can inspect
it.

### In-depth insights

- **MemFS** is the memory filesystem: a directory of markdown files
  in a local git repo; every change is versioned by git with
  commit messages from the agent itself.
- **Context Repositories** generalise this: agents have programmatic
  shell + coding access to the repo and can spawn memory subagents
  to restructure prior context — "learn in token-space" is their
  framing.
- **Sleep-time Compute** runs memory consolidation jobs while the
  agent is idle; **Skill Learning** lets the agent record reusable
  procedures.
- Reinforces Letta's own April 2025 finding that filesystem-backed
  memory is hard to beat — they shipped a product on top of that
  insight rather than trying to invent a "smart" store.

## mem0 v2 → v3 Algorithm Release

- Source: <https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm>,
  <https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning>,
  <https://docs.mem0.ai/migration/oss-v2-to-v3>
- Date: April 2026 (initial), with temporal-reasoning follow-up
  later in April/May 2026.

### Why it matters for local models

mem0 is the most-embedded memory layer in third-party agent
frameworks (LangChain, CrewAI, AutoGen), so a new algorithm version
changes the default that thousands of stacks ship with. The v3
algorithm is also distinctly cheaper at inference: one LLM call per
turn instead of two.

### In-depth insights

- New pipeline: context lookup → **single-pass** extraction →
  deduplication → built-in entity linking → write.
- Stores entities in a parallel collection `{collection}_entities`;
  retrieval matches query entities and uses them to boost the final
  combined score. Replaces external graph-store integrations with
  this built-in linking.
- ADD-only — memories accumulate rather than getting overwritten;
  no UPDATE or DELETE in the new algorithm.
- Reported gains vs. previous algorithm: **+29.6** on temporal
  queries and **+23.1** on multi-hop reasoning; **91.6 on LoCoMo**
  with the new algorithm (mem0.ai blog numbers; treat as
  vendor-reported until replicated externally).

## MemOS v2.0 — local plugin, OpenClaw plugin

- Source: <https://github.com/MemTensor/MemOS>
- Date: v2.0.19 latest release **June 12, 2026**; preceding plugin
  launches between April and June.

### Why it matters for local models

MemOS now ships a **100% on-device** plugin (SQLite + FTS5 + vector
hybrid retrieval) with no cloud dependency. That makes it directly
comparable to mem0 and Letta as a self-hostable memory layer on a
workstation.

### In-depth insights

- `memos-local-plugin 2.0` advertises "self-evolving memory: L1
  trace, L2 policy, L3 world model, and crystallized Skills."
- OpenClaw Cloud plugin claims **72% lower token usage** with
  multi-agent memory sharing (vendor number, unverified).
- Headline benchmark claim: "+43.70% accuracy vs. OpenAI Memory"
  and "35.24% token savings" — these are repo-level claims; the
  underlying benchmark and backbone are not always stated.
- Repo: 9.8k stars, 30 total releases, primarily TypeScript +
  Python.

## SuperLocalMemory — local-only LoCoMo SOTA claim

- Source: <https://github.com/qualixar/superlocalmemory>,
  <https://arxiv.org/abs/2603.14588>,
  <https://arxiv.org/abs/2604.04514>
- Date: latest release v3.6.3, **June 7, 2026**. Backed by three
  arXiv papers (Feb–Apr 2026).

### Why it matters for local models

Explicitly markets itself as "World's first local-only AI memory to
break 74% retrieval and 60% zero-LLM on LoCoMo." If the numbers
replicate, it's the strongest open-weight, zero-cloud baseline to
date — relevant for anyone running fully offline.

### In-depth insights

- Mode A (Zero-Cloud): **74.8%** aggregate on LoCoMo (1,276 Qs).
- Mode B (Local Ollama): comparable to Mode A.
- Mode C (cloud LLM): **87.7%** aggregate, **85.0% open-domain**.
- Claims **+10.6** percentage-point advantage over mem0's
  zero-LLM baseline (64.2%) — vendor-reported, treat with caution
  until replicated by an independent leaderboard.
- License: **AGPL-3.0** (commercial license required for closed-source
  integration) — a meaningful difference from Apache-2.0 frameworks
  like Letta and mem0.

## MemMachine — ground-truth-preserving memory

- Source: <https://arxiv.org/abs/2604.04853>
- Date: arXiv April 7, 2026.

### Why it matters for local models

Open-source, integrates short-term, episodic, and profile memory
within one architecture, and publishes a detailed ablation breakdown
that's useful as a recipe.

### In-depth insights

- **0.9169 on LoCoMo** with gpt-4.1-mini; **93.0%** on LongMemEvalS
  (the ICLR 2025 split) under a six-dimension ablation.
- Stores entire conversational episodes (avoids lossy LLM-based
  extraction); uses contextualised retrieval that expands nucleus
  matches with surrounding context.
- Ablation: retrieval-stage gains dominate ingestion-stage gains —
  retrieval depth +4.2, context formatting +2.0, search prompt
  design +1.8, query-bias correction +1.4, vs. sentence chunking
  +0.8. Suggests where to spend engineering effort.

## MemAgent (ICLR 2026 main-track Oral)

- Source: <https://iclr.cc/virtual/2026/oral/10007826>
- Authors: Yu et al.
- Date: ICLR 2026 (April).

### Why it matters for local models

The strongest 2026 result on extreme-context QA via a memory-update
policy rather than architectural change. The recipe — extend DAPO to
optimise the memory-update step — is reproducible on open-weight
backbones.

### In-depth insights

- Processes text in segments and updates memory via an overwrite
  strategy.
- Reported extrapolation from an **8K training context to 3.5M-token
  QA** with **<10% performance loss**.
- **>95% on the 512K NIAH** test.
- Memory update policy is trained end-to-end with an extended DAPO
  objective. (Not to be confused with the *MemAgents workshop*; the
  naming collision is unfortunate.)

## KV-cache as memory: AsymKV (NeurIPS 2025, June arXiv revision)

- Source: <https://arxiv.org/abs/2506.05410>,
  <https://github.com/the-scale-lab/Asymkv>
- Date: NeurIPS 2025 paper; arXiv first version June 5, 2025 — flagged
  here because the cleanest LongBench-LLaMA numbers were folded into
  spring 2026 KV-cache compression survey roundups
  (<https://www.marktechpost.com/2026/04/29/top-10-kv-cache-compression-techniques-for-llm-inference-reducing-memory-overhead-across-eviction-quantization-and-low-rank-methods/>).
  **This is not a since-April novelty**; included as context for the
  KV-as-memory thread.

### Why it matters for local models

Training-free compression, applicable on top of an existing local
checkpoint — directly usable in llama.cpp / vLLM forks.

### In-depth insights

- Observation: adjacent keys get similar attention weights (local
  homogeneity) while adjacent values are heterogeneous.
- AsymKV merges similar keys (lossy on the key side) and uses a
  mathematically-proven lossless value compression.
- On LLaMA3.1-8B, **43.95 average on LongBench**, vs. H2O 38.89; on
  the Synthetic reasoning subset 39.39 vs. H2O 14.75.

## Memory security: Sleeper Memory Poisoning and MemPoison

- Source: <https://arxiv.org/abs/2605.15338> (Sleeper),
  <https://arxiv.org/abs/2605.29960> (MemPoison),
  OWASP Agent Memory Guard mentioned in third-party coverage.
- Date: arXiv May 14 and May 28, 2026.

### Why it matters for local models

Local agents that wire mem0/Letta/MemOS into long-lived state are
exposed to exactly these attacks. Both papers focus on attacks that
*survive* selective-extraction memory mechanisms, which is the
default for every framework you'd actually run.

### In-depth insights

- **Sleeper Memory Poisoning**: an adversary plants content in an
  *external* document/webpage/repo so the assistant later writes a
  fabricated memory about the user; the poisoned memory can be
  dormant for many sessions before triggering. Reported
  write-success up to **99.8% on GPT-5.5** and **95% on Kimi-K2.6**
  (paper's words). Reported numbers should be treated with the
  understanding that these are end-to-end pipeline measurements
  (write + retrieve + use), not just write rate.
- **MemPoison** (arXiv 2605.29960) introduces three components:
  semantic relational bridge (trigger+payload extracted together),
  entity masquerading (trigger optimised to mimic named entities so
  it survives rewriting), and joint embedding optimisation (trigger-
  injected texts cluster tightly in embedding space). The attack
  reportedly survives memory-extraction filters and remains
  retrievable in a memory store containing thousands of benign
  records.
- OWASP shipped **Agent Memory Guard** as a reference runtime defence
  for the ASI06 threat class (per third-party coverage; primary
  OWASP page not verified here, flagged as **unverified**).
