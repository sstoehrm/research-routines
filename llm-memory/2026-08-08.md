# LLM Memory — 2026-08-08

## Summary

The two weeks since the 2026-07-25 report were quieter than the May–July
cycle, but three arXiv preprints stand out for local-model relevance. **Zero-Mem**
(arXiv 2607.29377) eliminates LLM calls from the entire memory lifecycle
outside final answering — a direct answer to the token-tax problem that has
made Mem0- and MemGPT-style stacks expensive when the "management LLM" is
your local 7B/14B backbone. **CrystalMem** (arXiv 2608.00303) formalizes a
new failure mode — "memory hysteresis," the capability loss that persists
after a byte-budget squeeze/recover cycle — and evaluates its fix
explicitly in edge–cloud and multi-tenant deployments, one of the few
in-window papers where local/edge is a first-class scenario. A Tsinghua/KEG
**filesystem-memory** paper (arXiv 2607.26637) formalizes the
"directory-of-markdown-files as agent memory" pattern that Claude Code and
others already run in production, and its most useful negative finding is
that better organization did not translate into better final answers for
any tested agent. On the multimodal side, **V-Mem** (arXiv 2608.01543) names
and attacks the modality gap and similarity–relevance gap in agentic
retrieval. Framework activity was concentrated in three repos: **LMCache
v0.5.3** landed cluster-wide coordination + AES-GCM cache encryption + day-0
Mamba/MoE support, **mem0** shipped four SDK/CLI releases that add
per-agent extraction instructions and delete/expiry flags, and **cognee
v1.4.1** rounded out ingestion and metadata handling. Notably absent: no
new release from Letta, MemMachine, MemOS, or Zep in the window.

## Filesystem-Based Memory for LLM Agents

- Source: <https://arxiv.org/abs/2607.26637>
- HF paper page: <https://huggingface.co/papers/2607.26637>
- Coverage: <https://aiweekly.co/alerts/study-filesystem-memory-halves-llm-agent-retrieval-cost>
- Date: 2026-07-29 (Tsinghua/KEG lineage — Zhou, Yu, Wei, Wu, Ouyang, Jiao, Pan, McAuley, Zhang, Yu, Han)

### Why it matters for local models

Filesystem memory (a directory of Markdown files, edited by tool calls) is
model-agnostic and requires only generic file I/O primitives — no vector
DB, no graph store, no hosted service. It composes naturally with any
local backbone that can call `read_file` / `write_file` / `grep`, which
covers essentially every local coding agent stack in production today.

### In-depth insights

- Formalizes three roles over a single filesystem:
  - **Management agent** — writes and re-organizes memory.
  - **Search agent** — answers user questions with citations back to files.
  - **Execution agent** — distills task trajectories into reusable "skills."
- Headline empirical result: organized filesystem memory can roughly halve
  retrieval cost at scale.
- Cautionary result: organization erodes over time for all but the
  strongest management agent, and — the finding that will land hardest —
  better organization did **not** translate into better final answers
  for any agent tested. Directly relevant to anyone tempted to spend
  local-model tokens on aggressive re-organization passes.
- License / code release: not confirmed from the abstract; check the PDF.

## Zero-Mem — Zero-Token Memory Operations for LLM Agents

- Source: <https://arxiv.org/abs/2607.29377>
- HN discussion: <https://news.ycombinator.com/item?id=49178608>
- Date: 2026-07-31

### Why it matters for local models

Every write / index / retrieval step runs without consuming prompt tokens.
For local deployments where the "memory management LLM" is the same 7B or
14B model that also serves the user, removing memory-side LLM calls is a
straight cost win: no additional GPU seconds, no context-window pressure,
no need to run a second model tier.

### In-depth insights

- Uses an entity–context graph plus a temporal hierarchy; the two views are
  weighted per query at retrieval time.
- Reports competitive results with LLM-in-the-loop memory systems on
  long-memory and long-context QA benchmarks while eliminating memory-side
  LLM token consumption. Encoder cost is accounted for separately.
- Establishes a clear architectural contrast with Mem0 / MemGPT / MemOS,
  all of which spend LLM calls on extraction, summarization, or reflection.
- Numbers/benchmarks and code release should be verified from the PDF —
  arXiv was not fetchable from this run.

## CrystalMem — Elastic Memory via Knowledge Crystallization

- Source: <https://arxiv.org/abs/2608.00303>
- Date: 2026-07-31 (Wu, Huang — South Dakota State University)

### Why it matters for local models

CrystalMem is explicitly evaluated in **edge–cloud** deployments and
**multi-tenant serving** — one of the few in-window papers where
local/edge is a first-class scenario rather than a footnote. The failure
mode it names ("memory hysteresis" — capability that does not come back
after a squeeze/recover cycle in the byte budget) is exactly what happens
on prosumer boxes with dynamic cloud quotas or edge devices under load.

### In-depth insights

- A sidecar that demotes entries across **four fidelity states** under a
  crystallization-energy schedule.
- Entries are ordered by advantage-weighted influence with dependency
  coupling.
- Evaluated across 7 environments, 17 methods, and 6 backbones; reported
  to achieve the highest restored capability in every setting. Per-setting
  score deltas should be pulled from the PDF before quoting.

## MemLens — Value-Aware Memory Management + Analytics

- Source: <https://arxiv.org/abs/2607.25992>
- Date: 2026-07-28 (Shandong University + Beihang + City University of Hong Kong)

### Why it matters for local models

Storage-limited local deployments benefit disproportionately from
principled forgetting. MemLens exposes a Shapley-style value estimator so
low-utility records can be pruned instead of persisted forever, and ships
an interactive dashboard over the full memory lifecycle for debugging.

### In-depth insights

- Treats memory records as first-class data objects.
- Compares management strategies through the same value-scoring lens.
- Not to be confused with the older *MemLens* multimodal-VLM benchmark
  (arXiv 2605.14906) covered in the July 2026 report — same name, unrelated
  work.

## V-Mem — Modality-Routed Retrieval for Multimodal Agentic Memory

- Source: <https://arxiv.org/abs/2608.01543>
- Date: 2026-08-02 (Kang, Jiang, Li, Li, Li)

### Why it matters for local models

Vision-capable local models (Qwen-VL, InternVL, Llama-Vision) increasingly
need persistent multimodal memory. V-Mem's routing avoids expensive
cross-modal comparison at retrieval time, which is the operation that
tends to dominate cost on a single-GPU multimodal serving stack.

### In-depth insights

- Names two failure modes:
  - **Modality gap** — queries land near same-modality content even in a
    joint embedding space.
  - **Similarity–relevance gap** — top-similarity ≠ actual evidence.
- Routes retrieval by the query's and target's inferred modality.
- Uses LLM-generated "anchors" (hypothetical captions or enriched
  multimodal anchors) to bridge modalities.
- Complements the July 2026 MemLens VLM benchmark and MemLens
  (management), which together define the current multimodal-memory
  evaluation baseline.

## Memory for Large Language Models (survey)

- Source: <https://arxiv.org/abs/2607.25380>
- Date: 2026-07-28 (Zhoubian, Zhang, Kharlamov, Tang — Tsinghua/KEG)

### Why it matters for local models

Useful practitioner reference for choosing between KV-based, adapter-based,
and external-store memory on a fixed budget. Its three orthogonal axes
(representation, update dynamics, persistence) are the cleanest published
scaffold to date for reasoning about whether a given local stack needs
Titans-style TTT, a Mem0-style external store, or just longer context.

### In-depth insights

- Axes: implicit vs explicit representation, offline vs online updates,
  short vs long persistence.
- Covers transient attention, recurrent state, parameter-efficient
  adaptation, and lookup storage under one framework.
- Formalizes granular mechanisms for memory writing, routing, state
  transitions, and consolidation.
- Analyzes hybrid architectures and system-level efficiency trade-offs.

## LMCache v0.5.3

- Source: <https://github.com/LMCache/LMCache/releases>
- Date: 2026-08-05
- License: Apache-2.0

### Why it matters for local models

LMCache is the de-facto tiered KV-cache layer for vLLM. The Mamba/MoE
day-0 support and runtime-elastic tiers in v0.5.3 directly benefit local
multi-model serving on prosumer or edge boxes, and it is the strongest
in-window artifact for the KV-as-memory line (see also C²KV from the July
report).

### In-depth insights

- **Fleet-wide key/token directory** built from cache events, via the
  multiprocess coordinator — cluster-wide coordination without a separate
  metadata service.
- Day-0 support for **MiniMax M3** (Mamba/MoE hybrid) and **Kimi K3**.
- Device-DAX L1 devices can be added and removed at runtime, no restart.
- **AES-GCM KV-cache encryption** in the serialization layer.
- MP mode gains multimodal support (encoder caching still pending).

## mem0 — SDK / CLI / integration cadence (Aug 1 → Aug 5, 2026)

- Source: <https://github.com/mem0ai/mem0/releases>
- License: mostly Apache-2.0; n8n integration flipped to MIT in v0.1.3

### Why it matters for local models

All in-window changes are pure-client. mem0 is model-agnostic and runs
happily against Ollama / vLLM / LM Studio endpoints; the new
`agent_custom_instructions` field, expiry, and delete-linked flags are
directly useful for multi-tenant local deployments where different agents
share one store but need different extraction behavior.

### In-depth insights

- **Python SDK v2.0.15 (Aug 1)** — pagination fix in delete ops and
  Supabase driver; default reranker changed to `gpt-5-mini` (swap this
  before pointing at a local backbone).
- **Python SDK v2.0.16 / Node v3.1.4 (Aug 4)** — new `referenceDate` and
  `keywordSearch` search params; metadata handling hardened against scope
  manipulation; vector-store validation improved.
- **Python SDK v2.0.17 / Node v3.1.5 (Aug 5)** — `agent_custom_instructions`
  (Python) / `agentCustomInstructions` (Node): a second extraction-instruction
  set that applies only to agent-scoped memories.
- **CLI Python v0.2.11 / Node v0.2.12 (Aug 4)** — adds `--custom-instructions`,
  `--expires`, `--delete-linked` flags.
- **n8n integration v0.1.3 (Aug 5)** — license flipped to MIT for the n8n
  Creator Portal.

## Adjacent items from just before the window worth reading now

- **MemOps** (arXiv 2607.12893, 2026-07-14) — pre-cutoff by a week but
  referenced heavily in the July 25 – Aug 8 discussion. Reframes memory
  eval as a *lifecycle-of-operations* problem (remember / forget / update /
  reflect); finds session-level retrieval beats turn-level retrieval, and
  that long-context models are weak at reconstructing ordered memory-state
  trajectories. Code: <https://github.com/MemTensor/MemOps>
- **Beyond Memory Leaderboards / Theoria** (arXiv 2607.16848, ~2026-07-22)
  — introduces two full-text scientific-memory benchmarks: **PAIM** (81
  papers, 66 audited Qs) and **PTr** (252 papers, 98 audited Qs). Concrete
  cautionary finding: on PAIM, Graphiti wins outright but uses ~**2.6M
  characters of retrieved context per query** — after normalizing
  retrieval budget, the lead disappears. Reads directly on the trust of
  most vendor memory-benchmark claims.
