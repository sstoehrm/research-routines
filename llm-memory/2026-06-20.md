# LLM Memory — 2026-06-20

## Summary

The two months since the last report sharpened the field along three
axes. (1) **Architectural test-time training** moved from
proof-of-concept to something you can bolt onto open backbones:
ByteDance Seed's *In-Place TTT* (ICLR 2026 oral) updates MLP
down-projection "fast weights" on Qwen3-14B and Llama-3.1-8B at
inference without retraining, NVIDIA Toronto's *TTT with KV Binding*
proves a broad family of Titans/MIRAS-style designs is equivalent to a
learned linear-attention operator, and Google's Behrouz/Mirrokni team
published the explicit MIRAS follow-up *"Language Models Need Sleep"*.
(2) **Agentic memory frameworks** continue to fragment rather than
consolidate: mem0 shipped a token-efficient algorithm and claims 92.5%
on LoCoMo at <7K retrieval tokens (vendor-published), Letta pivoted
its narrative to *Letta Code* and a 42.5% Terminal-Bench result,
MemOS shipped six minor releases in eight weeks, **Zep ended support
for its Community Edition** and consolidated OSS effort on Graphiti,
and **EverOS 1.0.1** and the *Memory OS* 6-layer Hermes-Agent stack
launched. (3) **Evaluation got harder, not easier**: *LongMemEval-V2*
shifted to long multimodal web-agent trajectories with 100M+ token
contexts, *BEAM* hit 1M and 10M token scales, *Memora* introduced
forgetting-aware metrics (FAMA), and an independent **locomo-audit**
found 156 scoring/citation issues in the original LoCoMo. The most
credible neutral harness remains supermemory's **MemoryBench** (MIT)
but it still lacks Letta and EverMemOS providers — the biggest
verification gap in the ecosystem. **No open-weight stack currently
sits at the top of either BEAM-10M or LongMemEval-V2**; the leaders
are all closed commercial memory products layered on frontier APIs.

## In-Place Test-Time Training (ICLR 2026 Oral)

- Source: <https://arxiv.org/abs/2604.06169>
- Code: <https://github.com/ByteDance-Seed/In-Place-TTT> (Apache 2.0)
- Date: 2026-04 (oral at ICLR 2026)

### Why it matters for local models

This is the single most actionable TTT result of the cycle for local
practitioners: a drop-in technique that updates only MLP
down-projection "fast weights" at inference time, with **no
architectural changes** to the base Transformer. Applied directly to
**Qwen3-14B-Base** and **LLaMA-3.1-8B**, which is exactly the backbone
class people actually serve on workstations.

### In-depth insights

- Continual-pre-training-style update on a small subset of parameters
  (MLP down-projection) during inference; clipping for stable updates.
- Reports RULER averages up to 128K context.
- Apache 2.0 weights/code path; runnable on a single workstation.
- Answers part of the previous report's open question about Titans /
  MIRAS reproductions on open backbones, though it is not a
  one-to-one Titans port — it is a different mechanism that achieves
  a similar effect (long-term in-weight memorization at test time).

## TTT with KV Binding is Secretly Linear Attention (ICML 2026)

- Source: <https://arxiv.org/abs/2602.21204>
- Code: <https://github.com/nv-tlabs/tttla> (NVIDIA Source Code License)
- Date: 2026 (ICML 2026)

### Why it matters for local models

A theoretical unification that demystifies the recent TTT/Titans wave:
proves a broad family of these architectures reduces to a learned
linear-attention operator, enabling fully parallel formulations. This
is the foundation downstream reproductions will use.

### In-depth insights

- Bridges "test-time memorization" with the established linear-attention
  literature.
- Practical consequence: parallel training is now possible for
  architectures that previously looked inherently sequential.
- Code is open but under NVIDIA's source-code license, not Apache —
  read it before forking.

## Language Models Need Sleep — Self-Modification and Memory Consolidation

- Source: <https://arxiv.org/abs/2606.03979>
- Date: 2026-06 (Google Research)

### Why it matters for local models

This is the direct conceptual follow-up to MIRAS from the original
team (Ali Behrouz, Farnoosh Hashemi, Vahab Mirrokni). It frames a
"sleep" paradigm that distills fragile short-term in-context memory
into long-term parameters via upward Knowledge Seeding distillation
and a recursive "Dreaming" phase — biomimetic memory consolidation as
a first-class architectural element.

### In-depth insights

- No open backbone reproduction yet; the paper's experimental setup
  does not name a specific Qwen/Llama target.
- Conceptual fit with In-Place TTT (which provides the *mechanism* for
  in-weight updates) is obvious; expect community attempts to combine
  the two.
- Closed-weight at present.

## Google Research Blog: Titans + MIRAS (refreshed)

- Source: <https://research.google/blog/titans-miras-helping-ai-have-long-term-memory/>
- Date: 2026-06-04 refresh

### Why it matters for local models

Refreshed blog confirms scaling to >2M-token effective contexts at
**760M params** with BabiLong outperforming GPT-4. Architecture
remains described in enough detail to be reimplemented, but Google
has still **not released weights** and the only open re-implementations
are (a) `kolejnyy/titans-lmm` (PoC) and (b)
`ai-in-pm/Titans---Learning-to-Memorize-at-Test-Time` (multi-agent
demo). Reproduction on Qwen3 / Llama 4 backbones is still the
single most-requested missing artifact in the field.

## mem0 — Token-Efficient Algorithm + Rapid Release Cadence

- Source: <https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm>
- Temporal-reasoning follow-up:
  <https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning>
- State of AI Agent Memory 2026:
  <https://mem0.ai/blog/state-of-ai-agent-memory-2026>
- Releases: <https://github.com/mem0ai/mem0/releases>
- License: Apache 2.0
- Date: April 2026 algorithm; SDK releases through June 2026

### Why it matters for local models

mem0 had the busiest release cadence of any open-source memory stack
in the window. The April algorithm drop is plug-in for any existing
mem0 deployment; the June SDKs added **native `embed_batch` for
OllamaEmbedding**, making local-only memory pipelines materially
faster, plus an OpenCode plugin that natively integrates the
"dream" consolidation cycle without an MCP-server dependency.

### In-depth insights

- **Algorithm**: single-pass ADD-only hierarchical extraction (no
  UPDATE/DELETE during extraction); multi-signal retrieval (semantic
  + BM25 + entity-match fusion).
- **Vendor-published benchmark claims**:
  - 92.5% on LoCoMo at <7K tokens per retrieval call (vs 25K+ for
    full-context).
  - +29.6 pts on temporal queries, +23.1 pts on multi-hop reasoning
    vs the prior algorithm.
  - A separate vendor post claims 94.4% on LongMemEval at <7K
    tokens/call.
- **Skeptical note**: none of these numbers have been independently
  reproduced in supermemory's neutral MemoryBench harness, and
  Zep's *"Lies, damn lies and statistics: is mem0 really SOTA?"*
  critique remains the public counter-position. Treat as upper-bound
  marketing until cross-checked.
- **Releases in window**: Python v2.0.6 (2026-06-13), v2.0.7
  (2026-06-17); Node v3.0.8 (2026-06-13), v3.0.9 (2026-06-17);
  OpenCode plugin v0.2.0 (2026-06-17). Major in-window fixes:
  Anthropic tool-format, Qdrant HTTPS, ChromaDB `$not` filter,
  LangChain community CVE bump.

## Letta — Pivot to Letta Code (memory-first coding agent)

- Letta Code launch:
  <https://www.letta.com/blog/letta-code/>
- Desktop app: <https://www.letta.com/blog/introducing-the-letta-code-app/>
- Red-teaming the Context Constitution (2026-05-06):
  <https://www.letta.com/blog/>
- Latest release: v0.16.8 (2026-05-14)
- License: Apache 2.0 (server)

### Why it matters for local models

Letta's center of gravity has shifted from "memory framework you plug
into your agent" to "Letta Code — a Claude-Code-style harness whose
selling point is the three-tier MemGPT memory". Standalone LettaBot
was archived and folded into Letta Code "Channels"
(Telegram/Slack/Discord/WhatsApp/Signal connectors, beta). The local
story is intact — server runs locally, talks to any OpenAI-compatible
endpoint — but the framing is now "the harness, with the model swappable".

### In-depth insights

- **Terminal-Bench**: Letta Code reports **42.5%**, #1 among
  open-source coding agents, 4th overall.
- **Three-tier memory** (core / archival / recall) preserved; skills
  stored as `.md` files auto-invoked when similar problems recur.
- **Context Repositories** use Git for memory version control
  (commit / branch / rollback).
- **Decouples agent memory from model provider** — swap models
  mid-session while preserving memory state.
- **v0.16.8** is a minor security patch (JSON-based transport for
  sandbox-to-server tool results, replacing pickle); no 0.17 line
  shipped in the window.
- **Open question follow-up**: Letta did **not** re-publish a
  filesystem-baseline comparison in this window. The Aug-2025 claim
  (74.0% on LoCoMo, beating mem0 graph's 68.5%) remains the most
  recent first-party Letta number against the filesystem baseline.

## Zep / Graphiti — Community Edition Sunset

- Announcement (2026-06-03):
  <https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/>
- Graphiti repo: <https://github.com/getzep/graphiti>
- License: Graphiti Apache 2.0; Zep server now effectively closed SaaS

### Why it matters for local models

Material consolidation event. Zep officially **ended support for Zep
Community Edition**; OSS effort now lives on Graphiti (temporal
knowledge graph) only. Self-hosters whose stack depended on Zep CE
need a migration path — Graphiti covers the graph layer but not the
full Zep API surface.

### In-depth insights

- Graphiti remains Apache 2.0; works with any OpenAI-compatible
  endpoint and is a credible local-only knowledge-graph memory layer.
- Zep CE code moved to `legacy/`.
- The Zep team's prior LongMemEval claim of 63.8% temporal-retrieval
  and "90% latency reduction vs baseline" has not been refreshed in
  the window, and the closure of CE makes independent reruns
  meaningfully harder.

## MemOS (MemTensor) — Six Releases in Eight Weeks

- Repo: <https://github.com/MemTensor/MemOS>
- License: Apache 2.0

### Why it matters for local models

Highest-tempo OSS memory-OS project of the cycle: v2.0.15 → v2.0.20
shipped between 2026-05-11 and 2026-06-18. Positioning is "the memory
layer for Hermes Agent / OpenClaw", with explicit local-first
design (SQLite + vector, FTS5 hybrid retrieval).

### In-depth insights

- New hook-based plugin system; "Reflect2Evolve" architecture for
  `memos-local-plugin` (mid-turn reasoning capture); lightweight
  memory mode; ARMS telemetry for Hermes v2 plugin.
- v2.0.20 (2026-06-18) refactored search-pipeline hooks.
- Project-self-reported "35.24% token savings" — **not independently
  audited** in the window; cite as vendor claim only.

## EverOS 1.0.1 + EverMemOS paper

- EverOS: <https://github.com/EverMind-AI/EverOS>
- EverMemOS: <https://github.com/EverMind-AI/EverMemOS>
- Paper (EverMemOS): <https://arxiv.org/abs/2601.02163>
- License: Apache 2.0
- Date: EverOS 1.0.1 released 2026-06-16; EverMemOS paper 2026-05-04

### Why it matters for local models

Self-evolving memory across agents, Markdown-as-source-of-truth,
SQLite + LanceDB, BM25 + vector hybrid retrieval. Designed as a
**portable memory layer** across Claude Code, Codex, OpenClaw, and
Hermes — i.e. one memory store, many harnesses. OpenAI-protocol
compatible; works with Ollama/vLLM via env-var override.

### In-depth insights

- May-2026 EverMind blog benchmarked EverOS vs mem0, MemOS, Zep, MemU
  on LoCoMo / LongMemEval and claims SOTA — **vendor-published**, no
  third-party replication located.
- Prior claim: 92.3% reasoning accuracy on LoCoMo (LLM-Judge).
- Defaults to OpenRouter chat + DeepInfra embeddings; override for
  fully-local serving.

## TMEM — Scaling Self-Evolving Agents via Parametric Memory

- Source: <https://arxiv.org/abs/2606.04536>
- Date: 2026-06

### Why it matters for local models

Compresses dialogue history into **LoRA fast-weights** via
lightweight online updates within a single episode — closest in
spirit to NVIDIA's January "context as training data" framing, but
with explicit Qwen3 backbones. Compatible in principle with the
llama.cpp / vLLM local stack, though the paper's experiments don't
show production deployment.

### In-depth insights

- Backbones evaluated: **Qwen3-4B** and **Qwen3-8B**.
- Benchmarks: LoCoMo, LongMemEval-S, multi-objective search,
  CL-Bench; reports gains over summary- and retrieval-based memory
  baselines.
- Open question this cycle: can the LoRA updates be applied
  in-process inside llama.cpp / vLLM serving loops, or do they
  require a separate training service?

## Doc-to-Atom — Compositional Parametric Memory

- Source: <https://arxiv.org/abs/2606.12400>
- Date: 2026-06

### Why it matters for local models

Builds on Sakana's Feb-2026 *Doc-to-LoRA*: decomposes each document
into typed knowledge atoms, each compiled into an independent
micro-LoRA adapter with a provenance retrieval key. The result is
**compositional parametric memory** — a clean "NVIDIA-style
cached-activation LoRA" target that is much smaller per-item than
full Doc-to-LoRA and lends itself to local serving.

## KV-Cache Compression: Still, LCLM, FastKVzip

- Still (single-pass amortized KV compaction):
  <https://arxiv.org/abs/2606.07878>
- LCLM (end-to-end context compression at scale):
  <https://arxiv.org/abs/2606.09659>, code
  <https://github.com/LeonLixyz/LCLM>
- FastKVzip (gating-based KV eviction):
  <https://arxiv.org/abs/2601.17668>, code
  <https://github.com/Janghyun1230/FastKVzip>

### Why they matter for local models

The cycle's three most directly-applicable KV-compression results,
all backbone-agnostic and evaluated on open-weight models.

### In-depth insights

- **Still**: per-layer Perceiver (~7M params/layer), trained once via
  KL-distillation against a frozen base model; compression ratios
  8x–200x; context lengths 8K–128K.
- **LCLM**: continual pre-training of a 0.6B encoder / 4B decoder pair
  at 1:4, 1:8, 1:16 compression; "production-ready" 16× compression
  with minimal accuracy hit.
- **FastKVzip**: lightweight sink-attention gates trained via
  forward-pass-only objective; ~70% KV eviction with near-lossless
  performance on **Qwen2.5-1M, Qwen3, Gemma3** families.
- **vLLM FP8 KV-cache** post (2026-04-22):
  <https://vllm-project.github.io/2026/04/22/fp8-kvcache.html> — two-level
  accumulation fix restores 128K needle-in-a-haystack accuracy from
  13% to ~91% on Hopper FP8 FlashAttention-3; 14.9% throughput gain
  at ~20K tokens on Llama-3.1-8B; 54% ITL-slope reduction on
  Blackwell B200; accuracy recovery 94–99% across Llama-3.1/3.3,
  Qwen3/3.5, gpt-oss-20b, Gemma-4-E2B. `--kv-cache-dtype fp8`.

## MemAgents ICLR 2026 Workshop — Accepted Highlights

- Workshop pages:
  <https://iclr.cc/virtual/2026/workshop/10000792>,
  <https://sites.google.com/view/memagent-iclr26/>
- OpenReview venue:
  <https://openreview.net/group?id=ICLR.cc/2026/Workshop/MemAgent>
- Recap: <https://mcml.ai/news/2026-05-06-mem-agents-workshop-at-iclr-2026/>
- Workshop held 2026-04-27, Rio de Janeiro; ~110 submissions.

### Why it matters for local models

The MemAgents workshop continues to be the central venue where
open-source memory frameworks publish alongside academic work. The
acceptances below are the items most relevant to local-deployment
practitioners.

### Selected accepted papers

- **LightMem** — <https://github.com/zjunlp/LightMem>, OpenReview
  <https://openreview.net/forum?id=PLkhOUxkHQ>. Three-stage pipeline
  (extraction → consolidation → retrieval) with a hierarchical memory
  tree built via non-parametric agglomerative clustering. The most
  operationally-portable memory stack of the workshop.
- **A-MAC (Adaptive Memory Admission Control)** —
  <https://arxiv.org/abs/2603.04549>. Frames "what to admit to memory"
  as a structured decision over 5 factors. Uses **Qwen 2.5 locally**
  for utility scoring. **Claims SOTA on LoCoMo F1 = 0.583** with
  31% latency reduction vs LLM-native memory baselines — directly
  beats mem0/Letta-style admission policies on the LoCoMo
  precision-recall tradeoff.
- **MemFactory** — <https://arxiv.org/abs/2603.29493>. First modular
  RL-training framework for memory operations
  (extraction/update/retrieval) with GRPO integration. Up to +14.8%
  relative gains over base models. Infrastructure paper.
- **StructMemEval** — <https://arxiv.org/abs/2602.11243>. New
  benchmark testing whether agents organize memory as ledgers,
  to-do lists, trees, etc. Finding: memory agents only succeed when
  explicitly prompted on structure; vanilla RAG fails.
- **MemoryCD** — <https://arxiv.org/abs/2603.25973>. 400K real
  Amazon-user sessions across 12 domains; 14 long-context LLMs × 6
  memory methods; ROUGE ≤ 0.222, NDCG@3 ≤ 0.610 — memory is far
  from solved on real lifelong personalization.
- **PERMA** — <https://arxiv.org/abs/2603.23231>, code
  <https://github.com/PolarisLiu1/PERMA>. Event-driven personalized
  memory benchmark; finds current memory systems cut cost but break
  persona coherence over long horizons.
- **VehicleMemBench** — <https://arxiv.org/abs/2603.23840>.
  Executable benchmark with 23 tool modules / 111 in-vehicle APIs.
- **Experiential Reflective Learning** — <https://arxiv.org/abs/2603.24639>.
  Heuristic-pool memory from single-attempt trajectories.

Note: **no MemAgents workshop paper explicitly reproduces Titans**.
The closest large-scale memory-architecture result at ICLR 2026 is
the main-track oral **"MemAgent"** —
<https://openreview.net/forum?id=k5nIOvYGCL> — multi-conv
RL-based memory scaling 8K → 3.5M context, 95% on 512K NIAH.

## Benchmarks: LongMemEval-V2, BEAM, EvoMemBench, Memora, MemFail

- LongMemEval-V2: <https://arxiv.org/abs/2605.12493>, site
  <https://xiaowu0162.github.io/longmemeval-v2/>, code
  <https://github.com/xiaowu0162/LongMemEval-V2>, HF dataset
  <https://huggingface.co/datasets/xiaowu0162/longmemeval-v2>
- BEAM + LIGHT: <https://arxiv.org/abs/2510.27246>, site
  <https://mohammadtavakoli78.github.io/beam-light/>, code
  <https://github.com/mohammadtavakoli78/BEAM>
- EvoMemBench: <https://arxiv.org/abs/2605.18421>
- Memora + FAMA: <https://arxiv.org/abs/2604.20006>
- MemFail: <https://arxiv.org/abs/2605.26667>
- LoCoMo audit: dial481/locomo-audit (156 issues — 99 score-corrupting)

### Why they matter for local models

The cycle's evaluation surface basically doubled. LongMemEval-V2 and
BEAM make it possible to differentiate memory systems at 10M-token
trajectory scales; EvoMemBench introduces a two-axis taxonomy
(memory scope × content); Memora's **FAMA** finally penalizes
reliance on obsolete memory; MemFail adds an adversarial
stress-test. Running a local stack against any one of these is
cheaper than reading a vendor blog post.

### Concrete numbers

- **LongMemEval-V2**: top in-paper baseline **AgentRunbook-C =
  72.5%** avg accuracy. Strongest RAG: 48.5%. Off-the-shelf coding
  agent: 69.3%. No external leaderboard entries yet as of 2026-06-20.
- **BEAM-10M leaderboard** (per Hindsight blog, 2026-04-02):
  **Hindsight 64.1% (#1)**, Honcho 40.6%, RAG baseline 24.9%.
  Critical finding: a 1M-token context window cannot solve this —
  memory is required.
- **LongMemEval-V1 commercial top**: OMEGA ~95.4% (vendor),
  ByteRover ~92.8%, **Letta ~83.2%**, mem0 ~49% (per third-party
  summary blogs). All on frontier APIs.
- **No open-weight stack is at the top of either BEAM or
  LongMemEval-V2**.
- **LoCoMo**: independent **locomo-audit** found 156 issues (99
  score-corrupting, 57 citation-only) — interpret all LoCoMo
  numbers (including ByteRover's 92.2% #1 claim) with that caveat.

## Open questions / follow-ups

- Reproduce Titans on Qwen3 / Llama 4 — still missing. Closest open
  artifacts remain *In-Place TTT* (mechanism, not Titans) and the
  Behrouz Sleep paper (concept, no code).
- Run LongMemEval-V2 / BEAM-10M against Letta + mem0 + filesystem
  baseline on the same local backbone (Qwen3-Coder-Next or GLM-5.2);
  publish the score deltas next cycle.
- Push for **Letta and EverMemOS as MemoryBench providers** — without
  them, the supermemory neutral harness can't refute the
  vendor-published numbers.
- TMEM and Doc-to-Atom both produce LoRA-shaped artifacts at
  inference time; investigate whether they can be applied in-process
  inside vLLM / llama.cpp serving without a separate training
  service.
- Track the "Memory OS" 6-layer Hermes Agent stack — primary source
  was unreachable this cycle.
- Watch for whether `claude-mem`-style local memory layers (see the
  Claude Code report) start using mem0 v2.0.7's `embed_batch`
  OllamaEmbedding to drop dependence on remote embedding APIs.
- Cross-check Mem0's 92.5/94.4% LoCoMo/LongMemEval numbers in
  MemoryBench under identical conditions — currently vendor-only.
- Zep CE migration: which projects that depended on Zep CE move to
  Graphiti, and which switch frameworks entirely.
