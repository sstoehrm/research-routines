# LLM Memory — 2026-07-18

## Summary

Since the previous report (2026-04-23), agent memory has continued to
consolidate as a first-class research area. The most visible development
is a wave of "memory OS" work: MemTensor's **MemOS v2.0 "Stardust"**
shipped both a substantial code release and an accompanying arXiv paper
in July 2026, and a MIT-licensed six-layer community stack for local
models ("Memory OS on Hermes") landed in early June. **Mem0's April
2026 algorithm redesign** posts the current best public numbers on
LoCoMo/LongMemEval (92.5 / 94.4), and **Supermemory's SMFS** ("Memory
as a Filesystem") reframes agent memory as a mountable kernel filesystem
with its own xAFS benchmark. On the paper side, arXiv IDs in the 2606.*
and 2507.* ranges reflect a sharp increase in new lifecycle-and-benchmark
work (MemOps, MRAgent, Infini Memory), and the co-located **ICLR 2026
MemAgents workshop** (Rio, April 27) drew ~110 submissions with an
emphasis on RL-trained memory managers (MemAgent, MEM1, MemGAS). Two
June/July KV-cache compression papers (**CompressKV**, **MosaicKV**) are
directly relevant to running long-context on local GPUs.

## MemOS: A Memory OS for AI System + MemOS v2.0 "Stardust"

- Source (paper): <https://arxiv.org/abs/2507.03724>
- Source (code): <https://github.com/MemTensor/MemOS>
- HF paper page: <https://huggingface.co/papers/2507.03724>
- Secondary coverage:
  <https://www.testingcatalog.com/memos-2-0-brings-open-source-memory-os-to-ai-agents/>
- Date: arXiv v1 July 2026; GitHub v2.0.23 released 2026-07-09
  (34 total releases across the code base).
- License: Apache-2.0 (verified on GitHub).

### Why it matters for local models

MemOS is one of the few projects that treats memory as an OS-level
resource for open-weight LLMs — self-hostable, with local plugins for
the Hermes and OpenClaw agents that require no cloud dependency. It
ships a unified API over graph-inspectable memory plus multi-modal
ingestion (text, images, tool traces, personas), which is what most
local-agent stacks lack today.

### In-depth insights

- Core abstraction is the **MemCube** — a standardized memory unit that
  encapsulates content plus provenance/versioning metadata, composable,
  migratable, and fusable across **parametric**, **activation**, and
  **plaintext** memory types.
- **MemScheduler** performs asynchronous ingestion; a multi-cube
  knowledge base isolates cross-user memory.
- Reported benchmark numbers: LoCoMo **88.83**, LongMemEval **89.20**,
  PersonaMem v2 **40.58**; maintainers claim **35.24% token savings**.
- With MemOS, OpenClaw's average task completion improves from **36.63%
  → 50.87%** across five agent tasks.
- Weaknesses: numbers trail Mem0's April 2026 numbers on
  LoCoMo/LongMemEval by ~4 and ~5 points respectively; no explicit
  comparison against Letta/Zep in the abstract.

## MIRIX: Multi-Agent Memory System for LLM-Based Agents

- Source (paper): <https://arxiv.org/abs/2507.07957>
- HF paper page: <https://huggingface.co/papers/2507.07957>
- Date: arXiv July 2026.

### Why it matters for local models

MIRIX ships as a packaged application that runs **screen-capture memory
locally** with "intuitive visualization and secure local storage" —
explicitly pitched for privacy, an unusually clean fit for open-weight
setups. It also targets multimodal (screenshots) memory rather than
text-only.

### In-depth insights

- Six memory types: **Core**, **Episodic**, **Semantic**, **Procedural**,
  **Resource Memory**, and **Knowledge Vault** — orchestrated by a
  multi-agent controller that dynamically decides which store to
  write/read.
- Reports **85.4% on LoCoMo** (SoTA in the paper's comparison table)
  and, on **ScreenshotVQA**, **+35% accuracy over a RAG baseline with
  99.9% less storage**.
- Limitation: LoCoMo 85.4 is well below Mem0 (92.5) and MemOS (88.83);
  their true edge is on the multimodal side.
- Code/weights release status not verified from the abstract alone.

## Mem0 v1.1 memory algorithm (single-pass extraction + multi-signal retrieval)

- Source (blog): <https://mem0.ai/blog/state-of-ai-agent-memory-2026>
- Benchmarks: <https://mem0.ai/blog/ai-memory-benchmarks-in-2026>
- Code: <https://github.com/mem0ai/mem0>
- Date: April 2026 (algorithm rollout); TypeScript v3.0.13 (2026-07-01)
  and Node CLI v0.2.11 (2026-07-13) since.
- License: Apache-2.0 (repo confirmed).

### Why it matters for local models

Mem0 is the reference open-source memory layer that most local-agent
stacks compare against; the April 2026 rework replaces the expensive
UPDATE/DELETE loop with a **single LLM call**, cutting p95 latency and
tokens dramatically — critical when the LLM is a locally-hosted 7B–30B
model where every extra call hurts.

### In-depth insights

- Redesign built on:
  - (a) single-pass hierarchical extraction (one LLM call, no explicit
    update/delete),
  - (b) entity linking across memories,
  - (c) multi-signal retrieval combining semantic + keyword + entity
    matching,
  - (d) temporal reasoning.
- Reported numbers vs. prior version:
  - LoCoMo **92.5 (+21 pts)**,
  - LongMemEval **94.4 (+27 pts)**,
  - p95 latency **−91%**, token consumption **−90%**,
  - **+26% accuracy overall**.
- Baseline for the +21/+27 gap is the previous Mem0 architecture;
  comparisons against non-Mem0 systems (Letta, Zep, MemOS) less clearly
  enumerated in the blog.

## Supermemory Filesystem (SMFS) — "Memory as a Filesystem"

- Source (research): <https://smfs.ai/research/memory-as-a-filesystem/>
- Blog: <https://blog.supermemory.ai/smfs-making-agentic-retrieval-55-cheaper-and-more-accurate/>
- Repo: <https://github.com/supermemoryai/smfs>
- xAFS benchmark: <https://huggingface.co/datasets/supermemory/xAFS>
- Date: May 2026 research launch; supermemory `server-v0.0.5`
  "pluggable embeddings for self-hosted" 2026-07-10.
- License: MIT (supermemory core, confirmed).

### Why it matters for local models

SMFS mounts a Supermemory container as a **real, kernel-level
filesystem** with semantic search embedded in path operations — meaning
any local coding agent (Claude Code, Codex, Gemini CLI on-device) can
address memory as `open()` / `ls` / `grep` without a bespoke API. It is
the most novel structural take of the quarter.

### In-depth insights

- Reported wins on the accompanying **xAFS** benchmark (110 audited
  questions, 13 cross-context corpora, 5 to ~10,000 files):
  - **95% Recall@15** with only ~720 extra tokens (**99.4% context
    reduction**),
  - **53.8% fewer tokens** and **53.1% lower cost per correct answer**
    at near-parity pass rate,
  - **3.0× fewer tokens** on Claude and **1.75× on Codex** end-to-end.
- Robustness claim: at 10,000 files a plain-filesystem agent falls to
  **69% accuracy** while SMFS holds at **81%**.
- Caveat: xAFS is Supermemory's own benchmark; independent
  cross-validation is still pending.

## ICLR 2026 MemAgents workshop

- Source (workshop): <https://sites.google.com/view/memagent-iclr26/>
- MCML writeup: <https://mcml.ai/news/2026-05-06-mem-agents-workshop-at-iclr-2026/>
- Virtual page: <https://iclr.cc/virtual/2026/workshop/10000792>
- Date: April 27, 2026 (Rio de Janeiro, hybrid).

### Why it matters for local models

First ICLR workshop explicitly framed around memory as the bottleneck
for agentic LLM systems — a strong forcing function for the field, and
a lot of the accepted posters target training memory managers with RL
(viable on open-weight base models).

### In-depth insights

- ~110 submissions; keynotes from Chelsea Finn, Jeff Clune, Mengye
  Ren, Aditi Raghunathan, Volker Tresp, Weiwen Liu, Fred Sala, and
  Jeff Pan.
- Selected posters / orals:
  - **MemAgent** — RL-trained agent that segments text and updates
    memory via overwrite; extrapolates from 8K → 3.5M-token QA with
    <10% performance loss.
  - **MEM1** — RL agent that solves long-horizon tasks in **constant**
    context.
  - **MemGAS** — multi-granularity association + adaptive selection
    over Gaussian Mixture Models.

## Memory OS on Hermes — 6-layer open-source memory stack

- Source (coverage):
  <https://www.marktechpost.com/2026/06/01/meet-memory-os-a-6-layer-open-source-memory-stack-built-on-top-of-hermes-agent/>
- Date: coverage 2026-06-01; positioned as a community stack.
- License: MIT (per the writeup).

### Why it matters for local models

Explicitly pitched as the **local alternative** to Mem0 / Zep / Letta —
the entire stack runs on the user's own machine, layered onto the local
Hermes agent runtime. Fills a real gap: most memory frameworks assume a
cloud vector DB.

### In-depth insights

Six layers:

- **L1 — Workspace files** (`MEMORY.md`, `USER.md`, `CREATIVE.md`)
  injected into system prompt each turn.
- **L2 — Session store** `state.db` (SQLite + FTS5) for full-text
  conversation search.
- **L3 — Structured facts** in `memory_store.db` using SQLite + HRR +
  FTS5 + trust scoring.
- **L4 — Forked Icarus fabric.**
- **L5 — Qdrant vector DB** (4096-d cosine + BM25 sparse).
- **L6 — Auto-curated LLM wiki.**

No published benchmark numbers yet.

## CompressKV — KV-cache compression for long-context inference

- Source: <https://arxiv.org/abs/2606.24467>
- HTML: <https://arxiv.org/html/2606.24467v1>
- Date: June 2026 (arXiv 2606).

### Why it matters for local models

Local inference of long-context open-weight models (Llama 4, Qwen 3,
GLM-5) is memory-bound by the KV cache; a technique that keeps ≥97%
task performance at 3% of the cache is directly deployable on consumer
GPUs where VRAM is the binding constraint.

### In-depth insights

- Instead of aggregating attention scores across heads, identifies
  **Semantic Retrieval Heads (SRHs)** that reliably attend to first /
  last tokens and to semantically important spans; keeps only tokens
  salient to those heads.
- Reported: **>97% of full-cache LongBench QA performance at 3% KV
  cache**; **90% Needle-in-a-Haystack accuracy at 0.7% KV storage**.
- Specific to **grouped-query attention (GQA)** architectures.
- Baseline comparisons vs. H2O / SnapKV not fully summarized in the
  abstract.

## MosaicKV — dynamic two-dimensional KV-cache compression

- Source: <https://arxiv.org/abs/2607.00760>
- Date: July 2026 (arXiv 2607).

### Why it matters for local models

Complementary to CompressKV; addresses the serving-side problem when
many local agents share GPU/CPU memory budgets — relevant for on-device
deployments where the KV cache is the dominant memory cost as context
grows.

### In-depth insights

- Where prior methods compress along either sequence or channel
  dimension, MosaicKV compresses along **both**, **dynamically per KV
  segment**, exploiting non-uniform importance within each vector.
- Adds a compressed-KV management subsystem that uses underutilized GPU
  and CPU memory to keep compressed caches close and accelerate
  attention.
- Concrete throughput numbers not extracted from the abstract; baseline
  gap vs. prior 2D approaches not verified.

## Memory is Reconstructed, Not Retrieved (MRAgent)

- Source: <https://arxiv.org/abs/2606.06036>
- HF paper page: <https://huggingface.co/papers/2606.06036>
- Date: 2026-06-04 (Shuo Ji, Yibo Li, Bryan Hooi).

### Why it matters for local models

Local agents rarely afford expensive retrievers; MRAgent's active
reconstruction traversal reduces LLM calls by iteratively pruning graph
paths based on evidence — meaning fewer, cheaper local inference calls
per turn.

### In-depth insights

- Represents memory as a **Cue–Tag–Content graph** where "associative
  tags" bridge fine-grained cues to content nodes; retrieval is replaced
  by iterative reconstruction driven by the LLM's own reasoning trace.
- Claims improved token and runtime efficiency vs. strong baselines.
- Exact numeric wins and per-benchmark scores not verified from the
  abstract; code release status not confirmed.

## MemOps — benchmarking lifecycle memory operations

- Source: <https://arxiv.org/abs/2607.12893>
- HTML: <https://arxiv.org/html/2607.12893>
- Date: 2026-07-14 (MemTensor, HKUST-GZ, Renmin U.).

### Why it matters for local models

Existing memory benchmarks (LoCoMo, LongMemEval) score only final-answer
correctness, which conflates different memory failures. MemOps is a
**diagnostic** benchmark for the write / update / read lifecycle —
useful for iterating on open-source memory stacks (Letta, Mem0, MemOS)
where developers need to know **which stage broke**.

### In-depth insights

- Frames failure modes as:
  - (a) missing a fact introduction,
  - (b) binding an update to the wrong target,
  - (c) reading a stale value after a correction,

  and scores each independently.
- Same lab as MemOS, so expect their system to reference-implement
  well; independent leaderboards likely to follow.

## Also worth flagging (partially verified)

- **Infini Memory** (arXiv `2606.10677`) — topic-document persistent
  memory, June 2026. Treats agent memory as maintainable topic-structured
  docs; each topic doc holds evidence, metadata, and revisable facts.
  Positioned against Zep / mem0 style approaches.
- **Letta** — v0.16.8 released 2026-05-14 (Apache-2.0). Product blog
  messaging says "Letta Code" is now the center of gravity and ranked
  #1 on Terminal-Bench for open-source agents; no new memory-architecture
  paper this quarter that we could verify.
- **Graphiti (Zep)** — v0.29.2 released 2026-06-08 (Apache-2.0).
  Bug-fix release focused on FalkorDB. Marketing framing continues to
  distinguish **Graphiti** (engine, temporal knowledge graph) from
  **Zep** (platform).
